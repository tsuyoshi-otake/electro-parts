# ADR-0016: 観測頻度は店舗ごとに宣言する(スイッチサイエンスは週 1、秋月は月 1)

- 状態: 採用(2026-09-07)
- 関連: ADR-0013(観測頻度は 1 か月に 1 回)、ADR-0009、ADR-0014、`config/<store>.json`、`.github/workflows/crawl-publish.yml`

## 背景

ADR-0013 で観測を 1 か月に 1 回と決めたとき、店舗は 1 つだった。2 店舗になって、1 回の観測にかかる費用が桁で違うことがはっきりした。

| 店舗 | 取得方法 | 1 回の費用 |
|---|---|---|
| 秋月電子通商 | 一覧ページの HTML 巡回 | 約 2,700 リクエスト、約 85 分 |
| スイッチサイエンス | Shopify のカタログ JSON(ADR-0014) | 約 54 リクエスト、約 2 分 |

全店舗で 1 つの頻度にするなら、安いほうを高いほうに合わせて捨てるしかない。

サイズは制約にならないことを実測した(23,000 商品 × 5 年、合成負荷)。

| | 月 1(60 run) | 週 1(260 run) |
|---|---|---|
| SQLite | 19.37 MB | 37.65 MB |
| 配信サイト合計 | 40.64 MB | 49.87 MB |
| 価格変化点 | 35,399 | 70,958 |

観測回数は 4.33 倍だが配信サイズは 1.23 倍にしかならない。変化点しか保存しないので、商品名・型番といった 1 商品あたりの固定費が観測回数で増えないためである。しかもこの合成負荷は「観測するたびに 1 % の商品の価格が変わる」モデルなので、現実より多く見積もった上限側の数字である。GitHub Pages の上限は 1 GB で、5 年後でもその 5 % に届かない。

**つまり頻度を決めているのはサイズではなく、相手サイトへの負荷である。**

## 決定

- 頻度は `config/<store>.json` の `observation.cadence`(`weekly` | `monthly`、既定は `monthly`)として**店舗ごとに宣言する**。
- スイッチサイエンス = `weekly`、秋月電子通商 = `monthly`。
- ワークフローは cron を 2 本持つが、**どの店舗がどちらに乗るかは書かない**。起動した cron から求める頻度を決め、各店舗の設定ファイルを読んで観測対象を選ぶ。選ばれなかった店舗は `--republish` で公開済みデータセットを維持する(観測は増えない)。
- マニフェストの注意書きは cadence から決まる(`sampling_interval` / `sampling_interval_weekly`)。
- `tests/integration/observation-cadence.test.ts` が、宣言された cadence に対応する schedule の存在と、その cron が実際にその周期であること(週次は日を固定せず曜日を固定する、など)、そして schedule ブロックに店舗名が書かれていないことを検査する。

## 理由

**観測頻度と標本間隔の注意書きは、同じ事実の 2 つの表明である。** 食い違うと、履歴の読み方そのものが誤りになる — 利用者は「記録に無い = 変化が無かった」と読むが、実際は「観測していなかった」かもしれない。ADR-0013 はこれを文章で警告したが、警告は破られる。だから両方を 1 か所(店舗設定)から導き、テストで固定した。

cron の隣に店舗名を書かないのは、そうすると設定と schedule が別々に編集できてしまうからである。ずれても誰も気づかない種類のずれになる。

**秋月を週 1 にしない理由**は、得るものと失うものが釣り合わないことである。得られるのは価格改定日の精度だけで、月 1 でも改定そのものは捉えられる。一方で相手から見ると「毎週来る 85 分・2,700 リクエストのクローラー」になる。`robots.txt` に `Crawl-delay` は無い(相手は下限を要求していない)ので、0.53 req/s はこちらが選んだ上限であって、相手が許した値ではない(ADR-0009)。拒否されたときに失うのは 1 回の run ではなく、その店舗の観測そのものである。

## 結果

- 月次 run は monthly の店舗だけを観測する。週次 run はスイッチサイエンスだけを観測する。どちらも他店舗は `--republish` で維持されるので、公開サイトから店舗が消えることはない。
- 日曜と 1 日が重なる月は 2 本の cron が同じ日に走る。`pages-publish` の concurrency グループが直列化するので、同時に 2 つの書き手にはならない。
- 利用者に見える文言が店舗ごとに変わるため、ユーザースクリプトは注意書きキーを 2 つ持つ。旧版のユーザースクリプトは未知のキーをそのまま表示する(誤った文言を出すよりはよい)。
- 秋月へのリクエスト数は変わらない。この ADR は負荷を増やさない変更である。

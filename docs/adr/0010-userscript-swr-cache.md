# ADR-0010: ユーザースクリプトの stale-while-revalidate キャッシュと LRU

- 状態: 採用(2026-09-06)
- 関連: `userscript/core/dataClient.ts`、`userscript/core/cache.ts`

## 背景

商品ページを開くたびにマニフェストと商品ファイルを取りに行くと、表示が遅く、Pages への無駄なリクエストが増える。逆にキャッシュだけだと新しい観測が反映されない。データは 1 日 1 回しか変わらない。

## 決定

- **表示は即座に、更新は裏で**: キャッシュにある商品はまず表示し(6 時間以内なら「最新」、それより古ければ「キャッシュ表示」)、その後で更新を確認する。
- 更新の判定は**マニフェストの `datasetVersion`**。マニフェストは 30 分の TTL でキャッシュし(`?b=<30 分バケット>` で CDN のキャッシュも揃える)、キャッシュ済み商品の `datasetVersion` と一致すれば商品ファイルは取りに行かない。違えば `?v=<datasetVersion>` 付きで取得する(バージョンごとに URL が変わるので、CDN の古いキャッシュを踏まない)。
- 404 は「まだ観測データにない」として**負のエントリ**をキャッシュし、同じ版のうちは再要求しない。
- 取得失敗(ネットワーク、非 JSON、契約検証エラー、`storeId` / `pageKey` の不一致)は例外にせず、あればキャッシュを「キャッシュ表示」として残し、なければ「取得できません」を出す(fail-open)。
- キャッシュは `GM_setValue` に保存し、キーは `eph:c<契約メジャー>:product:<storeId>:<pageKey>`。契約のメジャーが上がると自然に別キーになる。エントリ数は LRU で 200 まで、30 日を過ぎたものは無視する。

## 理由

1 商品ページで通信は最大 2 回、再訪は 0 回。`datasetVersion` を使うので「更新があったのに古い表示のまま」が 30 分以上続かない。

## 結果

- Tampermonkey のストレージ容量は数 MB 単位で問題ない(1 商品 1〜5 KB × 200)。
- ホストしているのが GitHub Pages なので `Cache-Control` は制御できない。`?v=` と `?b=` で代替する。

# ADR-0006: SQLite は git に入れず、最終化した状態を Pages に公開して次回の入力にする

- 状態: 採用(2026-09-06)
- 関連: `src/db/finalize.ts`、`src/pipeline/previousState.ts`、`.github/workflows/crawl-publish.yml`

## 背景

毎日のクロール結果をリポジトリにコミットすると、履歴が数百 MB のバイナリ差分で膨らみ、レビューも不可能になる。一方、Actions のランナーは毎回まっさらなので「前回の状態」をどこかから持ってくる必要がある。

## 決定

- 生スナップショット、SQLite、生成物はいずれも**git にコミットしない**。
- 各 run の終わりに DB を `VACUUM INTO` で最終化し、`integrity_check`、SHA-256、サイズ、スキーマ版、店舗別 run 数を `state.json` に書く。これを Pages の `state/` に**公開データと一緒に**デプロイする。
- 次の run は `previousStateUrl` から `state.json` と DB を取得し、検証してから使う。取得・検証に失敗したら run は**失敗**する(黙って空から始めない)。
- `--bootstrap` は公開状態が存在しないときだけ許可し、存在するときは拒否する。
- Actions の成果物として生スナップショット(既定 30 日)、レポート(90 日)、最終化した状態(90 日)を残す。ロールバックはこの成果物から `--previous-dir` で再公開する。
- 公開は 1 つの Pages アーティファクトで行い(原子的)、`publishable` のときだけデプロイする。concurrency グループで単一ライターにする。

## 理由

- GitHub Pages はリポジトリ外のストレージとして無料で使え、公開データと同じ配信経路で状態も配れる。
- 状態が公開されていることは、透明性(誰でも履歴 DB を検証できる)にもなる。

## 結果

- リポジトリが private のままだと Pages が使えない(プランの制約)。公開リポジトリにする。
- Pages のサイズ上限(1 GB)と 1 ファイル 100 MB の制約。5 年分でも DB は数十 MB(README のベンチ参照)。
- 状態 DB は誰でも取得できるので、個人情報を含めない(含めるべきものもない)。
- 信頼境界: `state.json` の SHA-256 は DB の改ざんを検出するが、`state.json` 自体は署名されていない。信頼の根は **自分のリポジトリの Pages オリジンを HTTPS で取得すること**であり、そのオリジンを制御できる相手はリポジトリも制御できる。署名を導入しても鍵は同じ場所にしか置けないので、Phase 1 ではやらない。
- 取得できない・検証に失敗した場合は run を失敗させる。404（未公開）だけが「履歴なし」として扱われ、それでも `--bootstrap` がなければ失敗する。

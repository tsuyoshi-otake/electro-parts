# ADR-0020: 審査に通る形をテストで固定し、Chrome ウェブストアに出す

状態: 採用 / 2026-09-07 / Issue #7 / userscript 0.4.1

ADR-0019 の「ウェブストアには出さない」を置き換える。第 2 のホスト束縛という構成自体は 0019 のまま。

## 背景と境界

zip をデベロッパーモードで読み込む形は、入れるたびに Chrome の警告が出て、自動更新もされない。利用者側から見れば「動くが、勧められない入れ方」であり、公開している意味が薄い。ストアに出せば普通の拡張機能として入り、更新も配られる。

境界: 表示するもの・取得するデータ・観測頻度は変えない(0019 と同じ)。審査そのものは人が受ける。ここで決めるのは**こちら側で決められる部分をどう固定するか**だけである。

## 決定

- ウェブストアに出す。同時に **zip の導線も残す**。自分でビルドして中身を確かめられることは、この種の拡張機能を人に勧める条件だと考える。
- **審査が機械的に見る条件はテストにする**(`tests/contract/chrome-web-store.test.ts`)。名前 45 文字・説明 132 文字の上限、Chrome が解釈できる版番号(1〜4 個の整数、各 65535 以下)、アップロードでは付けてはいけないキー(`update_url`、`key`)や権限を広げるキー(`web_accessible_resources`、`externally_connectable` など)の不在、`storage` とデータオリジン以外を要求しないこと、`eval`・`new Function`・動的 `import`・`XMLHttpRequest`・宣言していない `chrome.*` API が**バンドルに 1 つも無い**こと、そして**コンテンツスクリプトが `fetch` を含まない**こと(通信はワーカーだけ、という 0019 の決定が実際に守られている証拠)。
- **バンドルは難読化せず、先頭に出所を書く**。生成物であること、ソースの URL、`npm ci && npm run build:extension` で再現できること、リモートコードを実行しないこと、`content.js` の大半は生成された対応表(コードではなくデータ)であること。テストは行長の上限も見る — 最小化された 1 行 10 万文字のファイルは、審査側にとって読めないのと同じである。
- **スクリーンショットは生成物**にする(`scripts/build-store-assets.ts`)。E2E と同じ保存済み商品ページ・同じ未展開拡張を実ブラウザに読み込んで 1280×800 で撮る。手で撮った画像はパネルを変えた瞬間に古くなり、古い画像は「説明と機能の不一致」そのものになる。
- **先頭 2 枚は店舗をまたいだ価格比較**にし、その 2 枚だけは**公開済みデータセット**を読む。比較には 1 商品について両店舗の記録が要るが、リポジトリに入っているスナップショットは対応表のある組をどちらの側も含まない。ここで合成データを作れば「実際の動作ではない画像」になるので、代わりに自分の Pages(店舗ではない)を読ませ、実際に公開した価格を写す。残り 2 枚は保存済みスナップショットから作ったデータセットで撮り、ネットワークに出ない。
- **撮影プロファイルはショットごとに使い捨てる**。拡張は取得したマニフェストと商品を `chrome.storage.local` に持つので、プロファイルを共有すると公開データセットの版が保存済みデータセットの画像に混ざり、`publication in progress` という英語の注記がパネルに出る。掲載画像に出してよい文字列ではない。
- **プライバシーポリシーは公開サイトに置く**(`public/privacy.html` → `/privacy.html`)。収集しないことだけでなく、取得先である GitHub Pages に通常のアクセスログが残り得ることも書く。書かない方が短いが、それは嘘になる。
- **ダッシュボードに入れる文言は `docs/chrome-web-store-listing.md` に原本を置く**。単一用途の説明、権限ごとの理由、リモートコードの回答、データ使用の開示、登録料・2 段階認証などの前提条件まで含める。提出は転記作業にする。
- データ使用の開示は**全カテゴリ「収集していない」**と回答する。根拠は Google の定義(収集 = 端末外への送信)であり、商品ページの URL と商品番号はブラウザ内でのみ使い、送信も保存もしない。

## 理由

審査は人の判断だが、**落ちる理由の大半は機械的**である。文字数、版番号、余分な権限、読めないコード、実体のない説明。これらを「提出前に気をつける」項目にすると、気をつけなかった回に落ちる。テストに置けば、気をつけなくても落ちない。

生成物にする判断は ADR-0016・0019 と同じ理由による。掲載情報とパッケージが別々に手で書かれていると、片方だけ古くなる。スクリーンショットは特にそうなりやすく、しかも古い画像は審査で最も分かりやすい不一致になる。

zip を残すのは、ストアが唯一の入手経路になると、審査の都合で配布が止まったときに手段が無くなるからでもある。

## 結果

- ストア公開後、ストア経由の利用者には自動更新が配られる。**zip をデベロッパーモードで入れている利用者は自動更新されない**ので、README とランディングページは両方の導線を残す。
- **ストアは同じ版を 2 回受け付けない**。再提出のたびに `USERSCRIPT_VERSION` を上げる。ユーザースクリプトの版も一緒に上がるが、同じバンドルである以上それが正しい。
- プライバシーポリシー URL は公開済みである必要がある。**拡張の提出より先に Pages を更新する**(`privacy.html` が 404 のままだと審査に出せない)。
- デベロッパー登録(登録料 5 USD)・2 段階認証・連絡先の確認・提出・却下時の対応は人の作業として残る。`docs/chrome-web-store-listing.md` に手順として書いてある。
- 店舗サイトへのリクエストは増えない。この ADR も相手サイトへの負荷を変えない。

## 更新・検証手順

1. Verify: `npm test`。Expect: `tests/contract/chrome-web-store.test.ts` の 10 件が通る(上限・版形式・禁止キー・権限・リモートコード不在・content.js に `fetch` が無いこと・バンドル先頭の注記・`public/privacy.html` の存在と記述)。
2. Verify: `npm run build:store-assets`。Expect: `dist/store/` に 1280×800 のスクリーンショットが 4 枚。先頭 2 枚に「記録価格差(他店 − 閲覧中)」の行と 2 系列のグラフが写っており、どの画像にも「読み込み中」が無い。比較の 2 枚は公開済みデータセットを読むので **Pages を公開した後に撮る**。Chromium を使うので `npx playwright install chromium` が要る。実行後にブラウザプロセスが残っていないことも確認する。
3. Verify: 公開後に <https://tsuyoshi-otake.github.io/electro-parts/privacy.html> と拡張 zip を取得する。Expect: どちらも 200 で、zip の `manifest.json` の版が上げた版。
4. 提出は `docs/chrome-web-store-listing.md` の転記。Expect: 掲載情報・プライバシータブの全欄が同ファイルの文言と一致。これは人が行う作業であり、自動化していない。
5. 却下されたら、直すのは掲載情報かパッケージのどちらか。パッケージを直した場合は版を上げて再アップロードし、1〜3 をやり直す。

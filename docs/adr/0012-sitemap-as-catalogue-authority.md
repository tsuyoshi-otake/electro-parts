# ADR-0012: クロール対象はサイトマップから発見し、カバレッジの正解として使う

- 状態: 採用(2026-09-06)
- 関連: `src/collectors/akizuki/sitemap.ts`、`src/collectors/akizuki/listings.ts`、`src/collectors/akizuki/crawl.ts`、ADR-0004
- 置き換え: ADR-0004 の「18 ジャンル」という前提を更新する(ADR-0004 自体は有効)

## 背景

初版のクローラーは手書きのジャンル一覧(`/catalog/r/` を 18 件)を巡回していた。これは**カバレッジを誰も検証していない**設計で、実際に穴が空いていた。

- サイトマップが数える商品ページ: **13,027 件**
- 18 ジャンルで観測できた商品: **8,677 件**(66.6%)

商品 131975 のように、一覧に載っているのに巡回対象のジャンルに属さない商品は、ユーザースクリプトから見ると恒久的に「記録なし」になる。しかも欠落は**静かに**起きる。手書きの一覧は、それ自体が「何を取りこぼしているか」を答えられないからである。

`robots.txt` は `https://akizukidenshi.com/Sitemap_index.xml` を公開している。この索引は gzip の子サイトマップを指し、全商品ページ(`/catalog/g/g<販売コード>/`)と全一覧ページ(`/catalog/c/<slug>/` の分類ツリー 458 件、`/catalog/r/<slug>/` のジャンルタグ 1,412 件)を列挙している。

## 決定

- **巡回対象はサイトマップから発見する。** 設定に書くのは「どの系統を歩くか」(`collector.listingKinds`: `c` / `r`)だけで、個々の slug は書かない。`collector.genres` は raw schema 3 で削除し、設定に残っていれば起動時にエラーにする(黙って無視して穴を開けない)。
- **歩く系統は `c` + `r` の両方に固定する。** 実測(2026-09-06/07、全一覧を走査):

  | 系統 | 到達した商品 | リクエスト |
  | --- | --- | --- |
  | `c`(分類ツリー 458 件) | 11,098 / 13,027 (85.19%) | 777 |
  | `r`(ジャンルタグ 1,412 件) | 12,677 / 13,027 (97.31%) | 1,937 |
  | `c` ∪ `r` | **12,772 / 13,027 (98.04%)** | 2,714 |

  どちらか一方では足りない(`c` 単独で 1,929 件、`r` 単独で 350 件の欠落)。また**日によって系統を変えてはいけない**。coverageId が変われば ADR-0004 の欠落統計比較が毎回無効化され、片方にしか載っていない 1,674 件が「掲載終了 → 復活」を繰り返す偽の履歴になるからである。
- **サイトマップの商品集合をカバレッジの正解にする。** クロール後、商品集合の差を取る。
  - `uncovered`(サイトマップにあり、どの一覧にも出なかった)が `collector.maxUncoveredProducts` を超えたら run は `complete: false`(ADR-0004 により取り込まない)。**しきい値は 600**。実測の残差は 255 件で、無作為に抽出した 10 件は 10 件とも販売終了品だった(商品ページは残るが、どの一覧からも外されている)。これは欠陥ではなくサイトの正常な状態で、時間とともに緩やかに増える。0 にすれば毎日失敗し、無制限にすれば一覧系統が丸ごと壊れても気づけないので、累積の余地を残しつつ系統単位の破損(`c` が落ちれば +350、`r` が落ちれば +1,929)を検出できる位置に置いた。なお系統の破損は、一覧ページ自体のエラーとしても ADR-0004 で捕まる。
  - `unlisted`(一覧で見えたがサイトマップにまだない = 新商品)は警告のみ。
  - 差分は raw スナップショットの `catalog` ブロックに数値と先頭 20 件の販売コードとして残す。
- **一覧の 3,000 件上限は失敗ではない。** どの一覧も最大 50 ページ × 60 件で打ち切られる(`c0` のような全件カテゴリが該当)。打ち切られた一覧は `truncated: true` として件数照合から除外し、その商品が他の一覧で拾えているかはカバレッジ検査が判定する。
- **`coverageId` は系統名で表す**(`sitemap:c`、`sitemap:c+r`)。カテゴリが 1 つ増減するたびに coverageId が変わると、ADR-0004 の「前回と coverageId が違えば欠落統計を比較しない」が run のたびに発動してしまう。

## 理由

「取りこぼしがないこと」を、サイト自身が公開している一覧と突き合わせて**毎回機械的に証明**できる。手書きの設定では、穴は誰かが商品ページを開いて気づくまで残る。実際そうなった。

サイトマップは商品ページの `<lastmod>` を持たないため、差分クロール(更新された商品だけ取る)には使えない。使えるのは「全体像の照合」であり、この ADR はそちらだけを主張する。

## 結果

- クロール量が増える。サイトマップ 7 + `c` 777 + `r` 1,937 = 約 2,700 リクエスト、1.5〜2.25 s 間隔で約 85 分(平均 0.53 req/s)。Actions のジョブ上限 180 分内。ADR-0009 の予算と README の記載を更新した。
- 到達率は 66.6% から 98.04% になった。残る 1.96% は販売終了で一覧から外された商品で、原理的に一覧クロールでは取れない。
- サイトが新しいカテゴリを追加したら、設定変更なしに翌日から巡回される。
- サイトマップが読めない日は run 全体が失敗する。部分的な巡回を「完全」と称するよりよい(ADR-0004)。
- 副作用として、パーサーは分類ツリーで使われる**表形式レイアウト**にも対応が必要になった(ADR-0008 を参照)。手書きのジャンル一覧はたまたまカード形式だけを踏んでいた。

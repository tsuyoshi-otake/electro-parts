# ADR-0035: 拡張は対応表をページのスクリプトに入れず、開いた商品の分だけワーカーから読む

状態: 採用 / 2026-11-10 / Issue #93(案 D) / userscript・拡張 0.7.9

関連: ADR-0011(fail-open、`innerHTML` 禁止)、ADR-0017(店舗横断の対応表)、ADR-0018(対応表の生成、詰めた形式)、ADR-0019(拡張は第 2 のホスト束縛)、ADR-0020(審査に通る形)、`userscript/core/relations.ts`、`userscript/core/relationShards.ts`、`userscript/core/controller.ts`、`extension/background.ts`、`extension/host.ts`、`extension/messages.ts`、`scripts/build-extension.ts`、`tests/bench/extension-load.ts`

## 背景

- 対応表(5,631 組)は生成物 `userscript/adapters/productRelations.ts` として、ユーザースクリプトにも拡張の `content.js` にも丸ごと入っていた。0.7.8 の `content.js` は 3,814,044 B で、そのうち描画コードは約 18 万 B、残りが対応表である。
- `content.js` は対応店舗のページを開くたびに読み込まれ、読み込み時に表全体を `JSON.parse` して `ProductRelation[]` に戻し、全件を索引にしていた。**対応が 1 件もない商品のページでも同じ**である。
- 保存済みページでの実測(Chromium、10 回の中央値、`tests/bench/extension-load.ts`)では、拡張なしに比べてタブごとに JS ヒープが約 6.9 MB 増え、ページ内のスクリプト実行が 14〜16 ms かかっていた。1 ページが使うのは多くても数十組である。

## 決定

1. **コアは「1 商品の対応」を非同期に尋ねる(`RelationSource`)。** `relationsFor(storeId, pageKey): Promise<readonly ProductRelation[]>`。コントローラーは索引(`relationIndex`)の代わりにこれを受け取る。表がどこにあり、どう分かれているかをコアは知らない。
2. **商品の履歴と対応は並行して読み、商品のパネルは対応を待たずに出す。** 対応の読み取りは商品の読み取りと同時に始める。履歴が先に届けば商品だけのパネルが出て、対応が届いた時点でカードが加わる。対応のカードは商品なしでは表示しない(従来どおり)。他店の履歴の取得(1 ページ最大 8 件・同時 2 件、ADR-0018)は、両方がそろってから始める。
3. **対応は付加情報なので、得られなければ商品だけを表示する(fail-open、ADR-0011)。** 失敗・10 秒(`RELATIONS_WAIT_MS`)の無応答・パネルの破棄のどれでも待ちは終わり、警告を 1 行ログに出すだけで、パネルにエラーは出さない。上限を過ぎてから届いた応答は捨てる。
4. **拡張では表を `content.js` から出し、パッケージ内の JSON ファイルにする。** `relations/index.json`(商品 → 分割番号)と `relations/shard-00.json`〜`shard-63.json`(詰めた形式の表、ADR-0018)。コンテンツスクリプトはワーカーにメッセージ `eph:relations-for` を送り、ワーカーが索引とその商品の分割 1 つだけを読んで、その商品の対応を返す。
5. **分割は対応のグラフの連結成分ごとに行う(`shardRelations`)。** 商品を頂点、対応を辺とみて、つながった商品はすべて同じ分割に入れる。こうすると、ある商品の対応はすべてその商品の分割にあり、どの対応も 1 回しか保存されない。成分は対応の数が多い順に、その時点で最も軽い分割へ置く(対応の数が同じ成分は表で先に現れた順、重さが同じ分割は番号の小さい順)。同じ表からは同じ結果になり、分割の数は 64 に固定する。
6. **ワーカーはパッケージ内の自分のファイルしか読まず、ページにファイルを見せない。** パスは定数と検証済みの整数(0〜63)だけから作り、メッセージの文字列はパスに入らない。索引は自身のプロパティだけを引く(`Object.hasOwn`)。店舗 ID とページキーは 200 文字まで。送り主は自分の拡張 ID だけ(従来どおり)。`web_accessible_resources` は足さず、権限も増やさない。
7. **ワーカーは索引を持ち越さない。** MV3 のワーカーはいつでも止まるので、メモリに持つ状態を前提にしない。1 回の問い合わせで読むのは索引(約 86 KB)と分割 1 つ(28〜71 KB)で、どちらもパッケージ内のファイルである。
8. **ユーザースクリプトは表を持ったままにし、索引だけを遅らせる(`inMemoryRelations`)。** ユーザースクリプトは 1 ファイルで配るもので、別ファイルを置く場所がない。最初に尋ねられたときに 1 回だけ索引を作る。表示は変わらない。
9. **店舗の表示名は表と別の生成物にする(`userscript/adapters/storeLabels.ts`)。** 表示名は同期的に必要で、表と同じファイルにあると、拡張のコンテンツスクリプトが表ごと取り込んでしまう。`npm run matching:build` が両方を書く。

ADR-0019 の「ワーカーが受け付けるメッセージは 1 種類」は 2 種類になる。2 つ目はネットワークに触れない。ADR-0019 の境界(「`userscript/core` を変える必要が出たら、ホストの抽象が足りていない」)に従い、足りなかった抽象(対応の取得元)をコアに足した。

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 商品キーのハッシュで分割し、対応を両端の商品の分割に入れる | どの対応も 2 回保存される。最初の実装がこれで、zip が 790,249 B → 2,147,211 B になった |
| 表を 1 つのファイルにしてワーカーが読む | ページは軽くなるが、ワーカーが起きるたびに 3.5 MB を解析する。問い合わせ 1 回の仕事が表の大きさに比例したままになる |
| `web_accessible_resources` にしてコンテンツスクリプトが直接読む | 店舗のページからも読めるようになり、拡張の有無を調べる手段を与える。`content.js` に `fetch` を置かない契約テスト(ADR-0020)も崩れる |
| 対応を Pages のデータとして配り、商品ごとに取得する | データ契約(ADR-0007)の変更になり、対応のある商品で通信が 1 回増える。対応表はレビュー済みの版と一緒に配る前提(ADR-0018)も変わる。ユーザースクリプトの軽量化が必要になったら改めて検討する |
| `chrome.storage` や IndexedDB に表を展開しておく | パッケージと保存先の二重持ちになり、版が変わるたびに移行が要る |
| ワーカーが索引をメモリに持つ | 止まれば消えるので、持たない経路も結局必要になる。読むのは 86 KB で、節約は小さい |

## 実測

保存済みの秋月の商品ページ 2 つを、同じ未展開の拡張で開いた(Chromium、ウォームアップ 2 回のあと 10 回の中央値、通信はすべて手元で差し替え、2026-11-10)。「拡張なし」は同じページを拡張を入れずに開いた値。数値は CDP の `Performance.getMetrics` がページのレンダラーについて返すもので、ワーカー側の仕事(索引と分割 1 つの読み取り)は含まない。

| | 拡張なし | 0.7.8 | 0.7.9 |
|---|---|---|---|
| スクリプト実行(`ScriptDuration`、対応なしの商品) | 0.1 ms | 14.1 ms | 0.8 ms |
| スクリプト実行(`ScriptDuration`、対応 9 組の商品) | 0.1 ms | 15.7 ms | 0.8 ms |
| JS ヒープ(`JSHeapUsedSize`、GC 後、対応なしの商品) | 0.68 MB | 7.57 MB | 1.89 MB |
| JS ヒープ(同、対応 9 組の商品) | 0.68 MB | 7.85 MB | 2.18 MB |
| タスク時間の合計(`TaskDuration`、対応なし / 9 組) | 125.7 / 97.6 ms | 201.0 / 293.6 ms | 163.2 / 257.9 ms |
| パネルが出るまで(対応なし / 9 組) | — | 188 / 225 ms | 186 / 191 ms |
| パネル内の外部リンク数(対応なし / 9 組) | — | 1 / 39 | 1 / 39 |

パッケージの大きさ:

| | 0.7.8 | 0.7.9 |
|---|---|---|
| `content.js` | 3,814,044 B | 178,999 B |
| `background.js` | 2,771 B | 8,012 B |
| `relations/`(索引 + 64 分割) | — | 85,814 B + 3,520,789 B |
| 分割 1 つ | — | 27,528〜70,500 B(最大の分割は対応 384 組) |
| 展開後の合計 | 約 3.82 MB | 3,799,269 B |
| zip | 790,249 B | 960,471 B |

- 対応の内容は変えていない。`JSON.stringify(PRODUCT_RELATIONS)` の SHA-256 は変更の前後で同じで、契約テストは全商品について「索引 → 分割 → その商品の対応」が表から直接引いた結果と一致することを確かめる。
- 連結成分は 2,309 個、最大の成分は 32 商品・384 組で、これが最も重い分割の下限になる。
- **zip は約 22 % 大きくなる。** 文字列の表が分割ごとに重複し、ファイルをまたいだ圧縮が効かないため。インストール時に 1 回だけ払うコストで、ページを開くたびのコストと引き換えにした。契約テストは「zip が表全体の JSON の 0.32 倍より小さいこと」(現在 0.27 倍、対応を 2 回保存する配置では 0.61 倍)と「分割の合計が表全体の 1.3 倍より小さいこと」を見る。上限を表の大きさに比例させてあるので、対応表が増えても誤検知しない。

## 限界(受け入れたもの)

- **ユーザースクリプトは軽くならない。** 表を読み込み時に解析するのは従来どおりで、遅らせたのは索引の作成だけである。
- **拡張では、対応のカードが商品の履歴より少し遅れて出ることがある。** ワーカーへの往復が 1 回入るため。保存済みページでの実測では、パネルが出るまでの時間は変わらないか短くなった。
- **対応を読めなかったことは利用者には見えない。** 商品だけのパネルになり、理由はコンソールの警告にだけ残る。対応がない商品との区別は画面からはつかない。
- 1 つの成分が非常に大きくなると(現在の最大は 384 組)、その分割だけが大きくなる。分割の大きさは `tests/contract/extension-package.test.ts` が毎回測る合計とは別に、ビルド結果で確認する。
- **ワーカー側の時間とメモリは測っていない。** 実測の表はページのレンダラーの値である。ワーカーの仕事は 1 回の問い合わせにつき JSON 2 つ(約 86 KB と 28〜71 KB)の読み取りと解析で、表の大きさではなく分割の大きさに比例する。
- 実測は保存済みページ 2 つ・1 台の計測である。実店舗のページでの確認は、リリース前のローカル確認(CLAUDE.md)で行う。

## 戻し方

コードの変更を戻す(コミットの revert)。データ・設定・データ契約には触れていないので、公開済みのデータや利用者の保存設定の移行は要らない。ストアは同じ版を 2 回受け付けないので、戻す場合も版を上げて出し直す。

# ADR-0003: 店舗スコープの SQLite に変化点だけを順序非依存で取り込む

- 状態: 採用(2026-09-06)
- 関連: `src/core/history.ts`、`src/db/importSnapshot.ts`、`tests/property/import-order.property.test.ts`

## 背景

毎日 9,000 商品を観測すると、5 年で 1,600 万観測になる。ほとんどの観測は前回と同じ値であり、価格の変化は 1 日あたり 1 % 程度。再実行・再取り込み・遅れて届いたスナップショットも扱う必要がある。

(その後、観測頻度は月 1 回に下げた → ADR-0013。観測数は 5 年で約 78 万になり規模の前提は緩んだが、「同じ状態の連続を畳む」「取り込み順序に依存しない」という決定はどちらの頻度でも同じ理由で正しい。)

## 決定

- 系列は**変化点**(`[観測時刻, 状態]`)の列として保存し、同じ状態の連続は 1 点に畳む。
- 取り込みは `planInsert` / `applyPlan` で「その時刻の直前の状態」と「直後の点」を見て決める。結果として**取り込み順序に依存しない**(順不同で入れても、時系列順に入れた場合と同じ系列)。プロパティテストで検証する。
- 同じ `normalizedHash` のスナップショットの再取り込みは `already_imported` で no-op。同じ観測時刻に異なる内容が来たら `SnapshotConflictError`(履歴を黙って書き換えない)。
- 「その時刻に観測されなかった」ことは presence 系列で表す。掲載が途切れた期間は価格が「継続している」とは見なさない。
- SQLite は `node:sqlite` を使い、テーブルはすべて `store_id` を持つ。店舗ごとに別ファイルにはせず、店舗ごとの読み出し(`readStoreHistory`)で分離する。
- 在庫数は変化が頻繁なのでサンプル(`inventory_samples`)として保存し、保持期間を過ぎたものは日次のロールアップに畳む(`inventory_rollups`)。
- メタデータ(名前、型番、カテゴリ、URL)の変化は `metadata_events` に記録する。

## 理由

変化点だけなら 5 年分でも数十 MB に収まり(README のベンチ参照)、静的ファイルもそのまま小さい。順序非依存にしておくと、失敗した日の再取り込みや成果物からの復元が安全にできる。

## 結果

- 「観測したが変化なし」という情報は `crawl_runs` にだけ残る。UI の「観測期間 (N 回)」はここから出す。
- 変化点の時刻は「初めて変化を観測した時刻」であり、実際の変更時刻ではない。契約の注意書き `sampling_interval` で説明する。

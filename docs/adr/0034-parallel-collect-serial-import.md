# ADR-0034: 店舗の収集は並列のジョブで行い、取り込みと公開は 1 つのジョブで直列に行う

状態: 採用 / 2026-11-10 / Issue #93(案 A)

関連: ADR-0004(不完全なクロールは取り込まない)、ADR-0005(隔離でも公開は続ける)、ADR-0006(状態の公開)、ADR-0009(アクセス間隔)、ADR-0030(毎日観測)、ADR-0032(秋月の cover クロール)、ADR-0033(観測できなかった店舗の通知)、`src/pipeline/collect.ts`、`src/cli/main.ts`、`.github/workflows/crawl-publish.yml`、[runbook](../runbook.md#収集ジョブと公開ジョブ)

## 背景

- これまでは 1 つのジョブが店舗を順に回し、pipeline の `collect` 段階がその中でクロールしていた。そのため run の長さは**店舗の所要時間の合計**になる。2026-11-07 と 11-09 の run では、秋月 約 90 分、スイッチサイエンス 約 40 分、M5Stack 約 21.5 分、せんごく 約 23 分、Pimoroni 約 30 秒で、合計 175〜184 分(ジョブ上限 240 分の 73〜77 %)。
- 直列にしていた理由は、1 つの SQLite 履歴・1 つの `state/`・1 つの `site/` を並行に書けないこと(ADR-0006)。これは**取り込み以降**の段階の制約で、ネットワーク待ちが大半の `collect` には当てはまらない。
- 各店舗は別のホストである。店舗 A を読んでいる間に店舗 B を読んでも、A が受けるリクエストの数・間隔・同時接続数は変わらない。
- 取り込み側には、収集済みのスナップショットを受け取る入口(`pipeline --snapshot`)がすでにある。

## 決定

1. **収集は店舗ごとのジョブ(`collect`、matrix)で並列に行う。** 1 店舗につき 1 ジョブで、そのジョブの中は従来どおり 1 本の直列クライアントである。同じ店舗を同時に 2 つのジョブが読むことはない(matrix の要素が店舗、run 全体は `pages-publish` の concurrency で 1 本)。
2. **取り込みと公開は 1 つのジョブ(`publish`)で、従来と同じ店舗順に直列で行う。** 履歴 DB・`state/`・`site/` の書き手は 1 つのまま。`publish` は収集ジョブが上げたスナップショット成果物を落とし、店舗ごとに `pipeline --snapshot` を流す。
3. **どの店舗を観測するかは `plan` ジョブが 1 回だけ決め、`collect` と `publish` はその結果を使う。** 2 つのジョブが別々に判定すると、日付をまたいだときに食い違う。
4. **収集の記録を成果物で渡す(`CollectRecord`)。** `crawl` コマンドがスナップショットと一緒に `reports/collect-<store>.json`(収集の完了可否、エラー、警告、指標、開始時刻、所要時間、スナップショットの SHA-256)を書く。`pipeline --snapshot FILE --collect-record FILE` はそれを `collect` 段階の結果としてレポートに写す。写さなければ、レポートからリクエスト数と収集時間が消え、隔離の理由(`collect error:`)が Issue に出なくなる(ADR-0033)。
5. **記録は、そのスナップショットのものであることを検証する。** 店舗 ID とスナップショットの SHA-256 が一致しなければ `collect` 段階を失敗にする。別の店舗・別の run の記録を取り違えて、正しくない指標や「完了」を写さないため。完了可否そのものは従来どおりスナップショット本体を検証して決める(ADR-0004)。記録は報告のためのもので、取り込みの判断には使わない。例外は観測時刻で、隔離した run の記録(`rejected_runs`)に書く時刻には記録の `retrievedAt` を使う(記録なしの `--snapshot` では従来どおり空)。同じ収集を 1 つのジョブで行ったときと同じ行になるようにするため。
6. **収集と書き出しの実装は 1 か所(`collectToFile`)に置き、pipeline の live 収集と `crawl` コマンドの両方がそれを使う。** 2 つの経路が別々に実装されていると、片方だけが `carryDir`(秋月の cover の記録、ADR-0032)を渡し忘れる、といったずれが起きる。実際、これまでの `crawl` コマンドは `carryDir` を渡していなかった。
7. **不完全な収集(終了コード 2)でも、収集ジョブは成功にしてスナップショットを上げる。** 取り込み側が従来どおり隔離し(ADR-0004、ADR-0005)、その店舗の公開済みデータを維持し、Issue で知らせる。収集ジョブを失敗にすると、隔離の記録(`rejected_runs`)が残らない。
8. **収集ジョブが落ちた店舗(スナップショットなし)は「失敗」として扱う。** `publish` はその店舗の pipeline を動かさず、`failed_stores` に入れ、既存の「サイトに無い店舗の復元」手順が公開済み履歴から再生成する。他の店舗の公開は続き(matrix は `fail-fast: false`、`publish` は `always()`)、ジョブは最後に失敗する。
9. **cover の記録のキャッシュは収集ジョブが持つ。** キーは `<store>-cover-…` で、秋月については従来と同じ系列なので、導入時に既存のキャッシュがそのまま使える。ワークフローには店舗名を書かない(`STORES` の 1 行だけ)。
10. **run の長さはジョブごとに測る。** `collect`(上限 150 分)と `publish`(上限 60 分)がそれぞれ自分の上限に対する割合を summary に出し、80 % を超えたら warning を出す(ADR-0033 の方式をジョブごとに適用)。

## ジョブの構成

| ジョブ | 依存 | 動く条件 | 上限 | 権限 | 内容 |
|---|---|---|---|---|---|
| `plan` | — | 常に | 10 分 | `contents: read` | 観測する店舗を決める。bootstrap の検査 |
| `collect`(店舗ごと) | `plan` | 観測する店舗があり、再取り込みでない | 150 分 | `contents: read` | `crawl` を実行し、スナップショットと収集の記録を成果物に上げる |
| `publish` | `plan`, `collect` | `plan` が成功していれば常に | 60 分 | `contents: read`, `actions: read` | 店舗順に取り込み、サイトを作り、検査して成果物に上げる |
| `deploy` | `publish` | 従来どおり | 従来どおり | `pages: write`, `id-token: write` | Pages へデプロイ |
| `alerts` | `publish` | `dry_run` でなければ常に | 従来どおり | `contents: read`, `issues: write` | 観測できなかった店舗の Issue |

## 検討して採らなかったもの

| 案 | 採らなかった理由 |
|---|---|
| 1 つのジョブの中で店舗をバックグラウンドプロセスとして並列に動かす | 成果物の受け渡しは要らないが、ログが混ざり、1 店舗のメモリ不足やタイムアウトがジョブ全体を止める。上限も合計で 1 つのままになる |
| 収集ジョブが取り込みまで行い、最後に DB を統合する | 履歴 DB の書き手が複数になる。順序に依存しない取り込み(ADR-0003)でも、`state/` の最終化は 1 つしか勝てない |
| 収集の記録を渡さず、スナップショットだけを渡す | レポートと summary から収集の指標と警告が消え、隔離の Issue に原因が出ない |
| 収集の記録をスナップショットの中に入れる | 生スナップショットは「店舗が返したもの」の記録で、再取り込みの入力でもある。収集の経過を混ぜると SHA-256 が収集のたびに変わる理由が増える |
| 同じ店舗への同時接続を増やす・間隔を詰める | 相手サイトへの負荷を上げる(ADR-0009)。この ADR は店舗**間**の並列だけを扱い、店舗**内**は直列のまま |

ADR-0032 は「並列取得(案 A)」を、同時接続とリクエスト密度が増えるものとして見送っていた。それは 1 つの店舗の中での並列を指した記述で、この ADR の案 A(別ホストどうしの並列)には当たらない。ADR-0032 の表にこの ADR への参照を足した。

## 負荷

| | 変更前 | 変更後 |
|---|---|---|
| 各店舗へのリクエスト数・間隔・同時接続数 | — | 変わらない(店舗ごとに 1 本の直列クライアント) |
| 1 日の run の長さ | 店舗の合計。175〜184 分(2026-11-07、11-09) | 最も長い店舗 + 取り込み。秋月が full の日で約 100 分、cover の日はスイッチサイエンスの約 40 分が支配する見込み。**実測は導入後の run で確かめる** |
| ランナーの使用時間(合計) | 約 180 分 | ほぼ同じ + ジョブごとの準備(`npm ci` など、1 ジョブ 1 分前後 × 店舗数) |
| Actions の成果物 | スナップショット(店舗ごと)、レポート、状態 | 収集の記録(店舗ごと、数 KB)が増える |

## 限界(受け入れたもの)

- **スナップショットの受け渡しが成果物に依存する。** 成果物のアップロードかダウンロードに失敗した店舗は、その日「失敗」になる(公開済みデータは維持され、Issue が出る)。クロールは済んでいるので、`reimport_snapshot_from_run` で取り込み直せる場合がある。
- **ジョブの準備が店舗数だけ増える。** Pimoroni のように 30 秒で終わる店舗も、1 ジョブぶんの準備(1 分前後)を払う。
- **ローカルの `pipeline`(live 収集)は従来どおり 1 プロセスで動く。** 並列化はワークフローの構成であって、pipeline の機能ではない。

## 戻し方

- ワークフローを 1 つ前の版に戻す(`git revert`)。`pipeline` の live 収集と `--snapshot` は従来の動作のまま残っているので、コード側を戻す必要はない。
- キャッシュのキーは同じ系列なので、戻しても秋月の cover の記録はそのまま使える。

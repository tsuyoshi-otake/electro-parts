# ADR-0032: 秋月は週 1 回だけ全一覧を読み、ほかの日は集合被覆で選んだ一覧だけを読む

状態: 採用 / 2026-11-09 / Issue #93(案 B)

関連: ADR-0004(不完全なクロールは取り込まない)、ADR-0008(表形式レイアウト)、ADR-0009(アクセス間隔)、ADR-0012(サイトマップを正解にする)、ADR-0030(毎日観測)、`src/collectors/akizuki/cover.ts`、`src/collectors/akizuki/crawl.ts`、`src/collectors/akizuki/collector.ts`、`config/akizuki.json`

## 背景

- 秋月の 1 run は一覧 1,871 件(分類 `c` 458、ジャンルタグ `r` 1,413)・約 2,711 ページで、1.5〜2.25 s 間隔のため約 85〜90 分かかる。全店舗の 1 run は約 2 時間 55 分で、ジョブ上限 240 分に対する余裕は約 65 分しかない(ADR-0030)。
- 所要時間は「リクエスト数 × 間隔」で決まるので、CPU や並列度ではなく**読むページ数**が支配項になる。間隔を詰める・並列にするのは相手サイトへの負荷を増やす方向なので採らない(ADR-0009)。
- 1 つの商品は平均 6.6 件の一覧に載っている(延べ約 84,000 件の出現、商品は約 12,818 件)。つまり同じ商品を毎日 6〜7 回読んでいる。

## 決定

1. **週 1 回(`fullCrawlEveryDays: 7`)は従来どおり全一覧を読む(full)。** それ以外の日は、直近の full が記録した「どの一覧にどの商品が載っていたか」から、全商品を覆う一覧の集まりを貪欲法で選び、それだけを読む(cover)。
2. **選び方(`planCover`)。** 重み = 一覧のページ数。1 ページあたりの未被覆商品数が最大の一覧から順に取る(同点は商品数が多い方、次に id が小さい方)。**カード形式で 3,000 件打ち切りでない一覧を先に取り**、残りの商品だけを表形式・打ち切りの一覧で覆う。理由は、カード形式だけが在庫数と購入可否を持つこと(ADR-0008、`isRicher`)と、打ち切られた一覧は順序次第で載る商品が変わり安定しないこと。貪欲法は最適解の近似だが、近似であることで欠落は生じない(全商品が覆われるまで取り続ける)。
3. **欠けた商品を足す(repair)。** cover の読み取り後に、前回 full にいて今回まだ見ていない商品を数える。残りがあれば、その商品を載せる未読の一覧のうち最も安いもの(カード形式を優先)を 1 件ずつ、`maxRepairListings`(40)まで読む。
4. **全部読み直す(escalate)。** repair の後でも `escalateAfterMissing`(30)件より多く欠けていれば、残りの一覧をすべて読んで full と同じ結果にする。これは「サイトが大きく変わった」ときの安全弁で、その日は従来と同じ時間がかかる。30 件以下の欠けは販売終了として警告に残し、受け入れる(`maxUncoveredProducts`・sanity しきい値は従来どおり効く)。
5. **ページの取得に 1 件でも失敗したら repair も escalate もしない。** 失敗した run は ADR-0004 により取り込まれないので、さらにリクエストを足さない。
6. **full に戻す条件(`decideCrawl`)。** どれか 1 つでも当たれば full にする。迷ったら full にする(毎日全部読んでいた従来の動作)。
   - `cover` が設定にない、一覧を明示した実行、前回の full の記録がない。
   - 記録した系統(`c+r`)が今回の系統と違う。記録の日付が未来。
   - 記録の経過が `fullCrawlEveryDays × 24 h − 6 h` 以上(毎日 05:00 JST 起動の run が数時間ずれても、ちょうど 7 日後に full になる。`FULL_CRAWL_SLACK_MS`)。
   - 選んだ一覧がサイトマップから消えている。
7. **記録を更新するのは、完全に終わった full(escalate した run を含む)だけ。** cover の run は記録を作り直さない。cover の run を重ねても経過日数が進み、必ず 7 日以内に full が来る。
8. **記録はキャッシュであって正本ではない(`carryDir`)。** pipeline が `state/work/carry` を collector に渡し、秋月は `akizuki-cover.json.gz`(gzip JSON、一時ファイルに書いてから rename)を置く。workflow は `actions/cache` の restore / save でこのディレクトリを run 間で持ち越す。読めない・形式が違う・欠けた記録は、厳密な検証(版、系統の並び、商品コードの昇順、一覧 id の形、ページ数 1〜50、全商品がいずれかの一覧に載ること)で弾き、**その日は full にする**。公開データ・履歴 DB・状態バックアップには含めない。
9. **各一覧の形式(card / table)を生スナップショットの `listings[].layout` に記録する。** 打ち切りは既存の `truncated`。`crawl` ブロック(`mode`、`reason`、`families`、`sourceBuiltAt`、`plannedListings`、`repairListings`、`missingAfterRepair`、`escalated`)は `cover` を設定したときだけ出す。`coverageId` は、読んだ一覧ではなく `raw.crawl.families` から作る(`sitemap:c+r`)。読んだ一覧の種類で決めると、cover の日に coverageId が変わり、ADR-0012 が避けようとした「欠落統計の比較が毎回無効化される」ことが起きるため。

## 実データでの確認

保存済みの実スナップショット 4 件(2026-11-04、11-06、11-08、11-09 の run、`complete`)で再現した。偽サイトに 11-04 の全一覧を載せて full を回し、そこで得た記録で、後の日の一覧を載せた偽サイトに cover を回し、同じ日に full を回した結果と突き合わせた。

| 11-04 の記録 → | 計画した一覧 | repair | 読んだページ | 全量(2,712)比 | 同日の full との商品集合・内容の差 |
|---|---|---|---|---|---|
| 11-06 | 596 | 0 | 857 | 32% | 0 |
| 11-08 | 596 | 3 | 898 | 33% | 0 |
| 11-09 | 596 | 3 | 898 | 33% | 0 |

- 欠けは 1 商品(後の日にサイトから消えていた)で、警告として残り受け入れられた。escalate は起きなかった。
- **保存済みの実スナップショットは形式を記録する前のものなので、すべてカード形式として扱った。** 実際の表形式の一覧の割合は、最初の full が `layout` を記録するまで分からない。表形式の一覧が多いほど計画は大きくなるため、上の 32〜33% は削減の上限側の見積もりである。
- 週あたりでは、cover 6 日(約 900 ページ)+ full 1 日(約 2,700 ページ)= 約 8,100 ページで、毎日 full の約 19,000 ページに対して約 57% 減る。cover の日の秋月は約 30 分(従来 85〜90 分)、週 1 回の full の日は従来どおり約 90 分。

## 検討して採らなかったもの

| 案 | 採らなかった理由 |
|---|---|
| 秋月の一覧を並列に取得する | 所要時間は縮むが、相手サイトへの同時接続とリクエスト密度が増える。ADR-0009 の「こちらが選んだ上限」を上げる話なので採らない。Issue #93 の案 A は別のもので、別ホストである店舗どうしを並列に収集する(店舗の中は直列のまま)。そちらは [ADR-0034](0034-parallel-collect-serial-import.md) で採用した |
| サイトマップの更新日で差分だけ読む | 商品ページの `<lastmod>` がない(ADR-0012) |
| `c` だけ・`r` だけを読む | 到達率が落ち、coverageId も日ごとに変わる(ADR-0012 の実測: `c` 単独で 1,929 件、`r` 単独で 350 件の欠落) |
| 読む一覧を手で固定する | サイトの変化に追従できない。集合被覆は毎週 full の結果から作り直すので、追従は自動 |
| 商品ページを 1 件ずつ読む | 約 12,800 リクエストで、全一覧より多い |

## 負荷

| | 変更前 | 変更後 |
|---|---|---|
| cover の日(週 6 日)の秋月 | 約 2,711 ページ・約 85〜90 分 | 計画 約 860〜900 ページ・約 30 分(上の実データ再生。形式が未記録なので上限側の見積もり) |
| full の日(週 1 日)の秋月 | 同左 | 同左。回数だけが減る |
| 週あたりの秋月への一覧リクエスト | 約 19,000 | 約 8,100(約 57% 減) |
| 全店舗の 1 run | 約 2 時間 55 分 | cover の日は約 2 時間にまで縮む見込み。full の日は同じ。**実測は導入後の run で確かめる** |

アクセス間隔・ジッター・再試行上限・`maxRequests` は変えない。1 リクエストごとの負荷は同じで、来る回数が減る。repair と escalate は上限があり(`maxRepairListings` 40 一覧)、escalate した日は従来と同じ量に戻るだけで、それを超えない。

## 限界(受け入れたもの)

- **新商品の発見が最大 7 日遅れることがある。** 新商品が計画した一覧のどれかに載れば当日に見える(カード形式の一覧が 1 つでも載ればほぼそうなる)。計画に入っていない一覧にしか載らない新商品は、次の full まで見えない。見積もりでは新商品の約 1 割。サイトマップに現れた新商品は、従来どおり `catalog.unlisted` の警告に出る。
- **cover の日は、一覧の中での位置(`sourceListings`、`sourcePage`、`positionOnPage`、`duplicateOccurrences`)が full と違う。** これらは履歴にも公開データにも使われていない(生スナップショットの調査用の情報)。商品名・型番・分類・価格・在庫は full と同じ(実データ再生で差 0)。
- **記録の元になる full が表形式の一覧を多く含むと、削減は小さくなる。** 最初の full で `layout` が記録されるまで、正確な削減率は分からない。
- **導入した日の run は full で、cover は翌日から。** 記録のキャッシュが 7 日使われずに破棄された場合も、その日は full。
- キャッシュが書き換えられていた場合、悪意のある記録は「読む一覧を減らす」ことしかできない(別のホストのページは読めず、一覧 id は `c/…` `r/…` に限る)。取りこぼしは、サイトマップの照合(`maxUncoveredProducts`)と sanity しきい値(件数 20%・欠落 20%)が従来どおり検出する。

## 戻し方

- 設定だけで戻せる。`config/akizuki.json` の `collector.cover` を消せば、毎回全一覧を読む(`crawl` ブロックも出ない)。
- cover を残したまま毎日 full にするなら `fullCrawlEveryDays` を `1` にする。
- 手順は [runbook](../runbook.md#秋月の-cover-クロール) にある。

## 追記: 実サイトでの最初の full(2026-11-10)

定期 run 42743844544(2026-11-10、cover の記録が無い初日)。ログは `[crawl] no cover source (ENOENT)` → full、`cover source written: 1756 listings, 12821 products`、キャッシュ `akizuki-cover-42743844544-1` を保存。生スナップショット(`akizuki-2026-11-10T04-06-13-601Z.json.gz`、`complete`)の `crawl` は `mode: full`、`reason: no cover source from an earlier full run`、`plannedListings: 1871`、`escalated: false`。収集は 5,411.7 秒、2,718 ページ、失敗ページ 0。

`listings[].layout` の内訳(1,871 一覧、読んだ一覧ページ 2,711):

| 形式 | 一覧 | ページ | ページの割合 | 載っていた商品(延べ) |
|---|---|---|---|---|
| card | 1,751 | 2,590 | 95.5% | 84,176 |
| index(商品を載せない目次) | 115 | 115 | 4.2% | 0 |
| table | 5 | 6 | 0.2% | 269 |

- **表形式は 5 一覧・6 ページだけ**(`c/cantenna-`、`c/cbatbox`、`c/cdrivekit`、`c/cheatsink`、`c/cscrew`)。「表形式が多いと削減が小さくなる」という限界は、今のサイトではほぼ効かない。
- 3,000 件で打ち切られる一覧は 2 つ(`c/c0`、`r/rparts`、どちらも card・50 ページ)。
- このスナップショットから記録を組み直し(1,756 一覧・12,821 商品で、ログの件数と一致)、`planCover` に渡すと **561 一覧・821 ページ(2,711 の 30.3%)**。表形式の一覧は計画に入らず、打ち切りの一覧が 1 つ入る。保存済みスナップショットでの再生(596 一覧・857〜898 ページ、32〜33%。こちらは repair のページを含む)と同じ水準。これは手元での組み直しによる見込みで、ランナーが保存した記録そのものを読んだ値ではない(スクリプトと出力は `~/tmp/pc93-real/`)。
- 翌日の run が実際に cover になり、`plannedListings` がこの前後になるかは、次の定期 run で確かめる。

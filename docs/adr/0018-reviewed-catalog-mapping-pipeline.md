# ADR-0018: 保存カタログの候補探索と承認済み対応表の再生成を分離する

状態: 採用 / 2026-09-07 / Issue #5 / userscript 0.4.1

## 背景と境界

初回80組だけを手編集しても、調査の偏りや型番の取りこぼしを検出できない。商品名の近さだけでは、Picoの無線・MCU・実装状態や、異なるメーカーの同じ数字を区別できない。[ADR-0017](0017-cross-store-comparisons.md) の価格比較承認は維持し、探索・判断・配信を分ける。履歴DB、店舗内の商品同一性、クロール頻度は変えない。

## 決定

| 役割 | 正本・実装 |
|---|---|
| 価格・在庫を除いた元商品情報、ID、URL、取得日時、元ファイルSHA-256 | `data/matching/catalog.jsonl` |
| 型番候補の全件一覧とフィンガープリント（生成物） | `data/matching/candidates.jsonl` |
| 候補ごとの明示的判断・根拠・不足情報・照合日 | `data/matching/reviews.json` |
| 初回80組の原判定・モデル情報・価格承認 | `data/matching/legacy.json` |
| 明示的に選んだ製品本体・特徴・公式仕様URL・照合日 | `data/matching/families.json` |
| メーカー別母数・未照合数・判断数・残件（生成物） | `data/matching/coverage.json` |
| 実行時対応表（生成物、直接編集禁止） | `userscript/adapters/productRelations.ts` |

- `scripts/matching/catalogs.ts` は2店舗の保存カタログを明示的に取り込む。メーカー型番と店舗SKUを別々に保持。メーカーと対応を確認した接頭辞だけを正規化し、リビジョン等の末尾は残す。SSの販売IDと同じ数字のSKUは型番探索に使わない。数字だけのメーカー型番は排除せず、衝突を個別判断する。
- `model.ts` は型番索引で探索する。入力文字列量Nと一致候補処理量Kに対して O(N + K)、出力Rの安定整列は O(R log R)。全カタログ同士の直積や表示件数による探索打ち切りはしない。メーカー不明・未一致は同一性の証明でも対象外の証明でもない。
- `generate.ts` は候補発見から同一商品を自動承認しない。判断は元行のフィンガープリントと固定し、元情報の変更・孤立判断・重複・不完全な製品群定義はエラーで停止する。未レビュー候補は実行時表へ追加されない。日次クロールから表を書き換えない。
- 類似は明示的な13製品群の本体だけを対象とする。1群64行以下の範囲内で店舗をまたいで仕様差を計算し、差分数の小さい順に表示する。名前一致でケーブルやケース等を混ぜない。既存判断（要確認・却下を含む）を製品群が上書きしない。型番・容量等が矛盾している行は要確認に残す。
- 商品照合と価格承認は独立。新しい同一商品は保存カタログ照合であり、販売数量・付属品・現行仕様・互換性を全件ライブ確認したという主張ではない。価格承認は従来の2組のみ、90日再確認条件も変更しない。
- 実行時は全リンクを残し、優先順に他商品最大8件の履歴を最大2件同時で取得する。上限以降は `reference_only` の明示的終端状態となり、取得待ちとして残さない。失敗manifestの共有・429再試行なし・描画からの取得なしを維持する。
- UIは既存テーマと無アニメーション方針を維持。差分・元型番・元データ取得日の表示を閲覧中→他店で統一する。埋め込み欄自体が狭い場合もコンテナクエリで縦に並べ、グラフの列が潰れないようにする。
- 現行SSコレクターは、既に受信している `body_html` と `tags` を任意フィールドとして生スナップショットへ保存する。追加リクエストも説明文からの自動MPN抽出も行わず、HTMLは画面に挿入しない。旧スナップショットとの互換性を維持。次の調査の根拠を失わないための保存であり、必ずメーカー型番が含まれる保証はない。

## 0.4.1の範囲と残件

元データは秋月2026-09-06取得8,677商品、SS2026-08-02取得10,343商品、合計19,020行。フィールドと取得日時の正確な値は `coverage.json` を参照する。現在の公開履歴にある商品数とは違い、現行全カタログ・他店舗・全別名・説明文の近似探索は範囲外。

最初の英数字一致191組だけで終わらせず、数字型番と確認済み接頭辞を含めて309候補を判断した。同一293、矛盾・情報不足による要確認6、数字衝突等による却下10、未判断0。これは採用率の目標ではなく、固定入力での再現結果。

初回判断と13製品群を合流した実行時表は424組。同一照合済み293・同一候補3、類似照合済み108・類似候補6、要確認14。製品群はPico、Pi5、Pi4、Touch Display 2、UNO R4、Nano R4、Nano 33 IoT、UNO Q、Opta、ATOM、Core2、Basic、PoE Camera。同じ製品群でも互換性・置換可能性は保証しない。

例: Pi5のSC1110は片側の名前が1GB、他側が2GBで矛盾するため、型番一致で承認しない。DFR0017のV3/V3.1、LattePandaのライセンス、MD10Cの定格、Raytacの書込状態、Featherの色も要確認に残した。型番探索に出なかった初回同一候補3組（T80、T-mini Plus、DFR0580）は候補のまま保持する。

## 更新・検証手順

1. Verify: `npm run matching:check`。Expect: 正本からの生成物がバイト単位で一致。CIも毎回実行する。
2. 元カタログを更新する場合のみ `node --import tsx scripts/matching/generate.ts --import-left <秋月保存JSON> --import-right <SS保存JSON>`。これは正本の差し替えであり、事前に差分を確認する。現行生スナップショットは旧保存カタログと形が違うため、そのまま指定しない。
3. Verify: `npm run matching:discover`。Expect: 全候補を再生成し、レビューと実行時表は変えない。メーカー別母数・未照合範囲を調べ、数行の表示を全候補と扱わない。続けて `npm run matching:names` を実行する。Expect: 未判定の名前の提案が0行。出た提案は組ごとに判定し、alias（同一商品・要確認・対象外）か製品群（類似商品）で記録する（0.6.5）。さらに `npm run matching:similar` を実行する。Expect: 未判定の類似商品の提案が0行。出た提案は組でつながる行ごとに判定し、製品群か `dismissals.json` で記録する（0.6.6。名前の語を共有しない基本型番の組は0.6.7）。
4. 根拠を再確認して `reviews.json` / `families.json` を編集する。フィンガープリントを一括で追認しない。`legacy.json` も原判定・モデル情報を保持して明示的に再評価する。販売条件を別途確認できなければ価格承認は加えない。
5. Verify: `npm run matching:build`、`npm run matching:check`、`node node_modules/vitest/vitest.mjs run --maxWorkers 2`、`npm run typecheck`、`npm run build:userscript`、`npm audit`。Expect: 全成功、欠落・重複・数字衝突・変更された根拠・周辺部品・負荷上限の回帰テスト成功。テストプロセスが終了したことも確認する。他リポジトリのテストは終了しない。
6. Verify: CIの保存ページE2Eと、AGENTS.mdの申請前確認に従った配布ZIPのローカルPlaywright確認。Expect: 実ページで両方向の差分、ライト/ダーク、系列・バリエーション切替が動作し、画像を確認済み。起動時間を制限し、終了後の対象プロセス残存0件を確認する。
7. バンドル更新時は版を上げてCI成功後 `gh workflow run crawl-publish.yml -f republish=true`。Verify: 公開バンドルと検証済みローカルビルドの版・バイト列、および公開前後の全店舗manifest/state。Expect: 新版一致、観測回数・データ版は不変。再クロールやbootstrapで履歴を作り直さない。

## 0.4.5: 3店舗と対象バリエーションへの拡張

M5Stack公式の完全スナップショットを既存の小売資料へ追記し、全店舗ペアを検索する。既存資料の自動更新は行わない。対象offer IDとSKUをレビューに記録し、同じページの異なる構成を生成時・表示時とも区別する。型番候補と異なるSKUを指定したレビューも拒否する。件数、要確認範囲、資料日付、更新手順は[3店舗の照合範囲](../roadmap/three-store-mapping.md)を参照。

## 0.4.9: 新しい完全スナップショットによる補完

状態: 採用 / 2026-10-04 / Issue #30 / userscript 0.4.9

固定資料のままでは、資料取得後に店舗へ追加された商品を探索できない。一方、既存行を新しい資料で上書きすると、判定済みの根拠が黙って変わる。そこで、既存行は固定し、新しい商品だけを補完ソースとして追記する。

- `--supplement <storeId>=<完全スナップショット>`（繰り返し可）。各店舗のコレクター検証で完全と判定された生スナップショットだけを受け付け、`catalogs.ts` の投影（SS名の連続空白の正規化を含む）で既存行と同じ形にする。
- 既存資料のどれにもない商品だけを追加する。補完ソースには元ファイル名・SHA-256・取得日時・追加件数 `count`・スナップショット全体の件数 `supplement.snapshotCount` を記録する。
- 既存行は名称・型番・variantが変わっていても固定し、変化した行数とスナップショットにない既存行を報告する。照合の根拠が変わった行だけ `--replace <storeId>/<pageKey>` で差し替え、旧行のキーを元ソースの `retired` に記録する。その行を根拠にした判定は指紋が変わって生成が停止するため、個別に再判断する。一括追認はしない。
- 差分のない差し替え、片方の資料にない行の差し替え、どの補完でも使われなかった `--replace`、追加も差し替えもない補完は停止する。
- `assertCatalog` の不変条件: 店舗順は最初のソース順（秋月→SS→M5Stack公式）。補完は同じ店舗の以前のソースより新しい日時で後ろに置く。`snapshotCount >= count`。ソースごとに「帰属行数 + `retired` 数 = `count`」。`retired` の各キーは同じ店舗のより新しい行に差し替え済み。
- 候補探索は全行（固定行・補完行）を対象にする。ペアの向きは店舗順に従い、既存の候補IDは変わらない。

2026-10-03の補完の件数、差し替え2行、新規候補90組の判断結果、範囲外は[3店舗の照合範囲](../roadmap/three-store-mapping.md#049の補完2026-10-04判定)を参照。

## 0.5.1: Raspberry Pi Shop by KSYの追加

状態: 採用 / 2026-10-29 / Issue #36 / userscript 0.5.1

- 新しい店舗の最初のソースは `--import-store <storeId>=<完全スナップショット>` で追記する（0.4.5の `--import-m5stack` を一般化）。その店舗のソースが既にあれば停止し、新しいスナップショットは `--supplement` で扱う。`catalogs.ts` は店舗ごとに検証関数と投影を表で持ち、未登録の店舗や不完全なスナップショットは停止する。
- KSYの名称・型番・URLは、公開履歴と同じ `normalizeKsyItem` から取る。実行時の `expectedNames` / `expectedModels` の照合が公開データの `current` と一致するためである。数値で返る型番は文字列にする。
- KSYの `make` は店舗のメーカー表示（「ラズベリーパイ財団」「KSY」「seeed」等）で、他店のメーカー名と表記体系が違う。`manufacturer` には入れず `vendor` に残す。候補探索のメーカー不一致による除外は `manufacturer` だけで行うため、表記差で候補は落ちない（`manufacturer` に入れた試行では93候補が落ちた）。メーカーの対応は組ごとのレビューで確認する。
- KSYソースは、保存済みの2026-10-29の応答を実コレクターに通した再現可能なスナップショットである。テストが同じ投影・SHA-256で `catalog.jsonl` の行とソース記録を再現する。
- 型番欄の店舗独自コード（`RAS…`）に埋め込まれた製品番号は取り出さない。店舗の加工品（ピンヘッダー実装版等）が元製品の番号を含むため、構成違いを同一商品として探索してしまう。
- 製品群（類似商品）は従来どおり秋月/SSの組だけで生成し、KSYの類似商品は出さない。

件数、要確認4組、統合確認で変更した1組、範囲外は[店舗間の照合範囲](../roadmap/three-store-mapping.md#051-ksyの追加2026-10-29判定)を参照。

## 0.6.1: せんごくネット通販の追加

状態: 採用 / 2026-10-30 / Issue #39 / userscript 0.6.1

- せんごくの最初のソースは、0.5.1と同じ `--import-store sengoku=<完全スナップショット>` で追記する。名称・型番・URLは公開履歴と同じ `normalizeSengokuItem` から取る（ADR-0024）。
- 店舗のメーカー表示は、KSYと同じく `manufacturer` に入れず `vendor` に残す。ただし型番の店舗接頭辞の規則（`M5STACK-`、`RPI-`、`ARDUINO-`、`DFROBOT-`）は既存の `identityCodes` がメーカー名で絞っているため、せんごくの4表記（`M5STACK`→M5Stack、`Raspberry Pi`→Raspberry Pi Trading、`Arduino`、`DFROBOT`→DFRobot）だけをその規則の入力に対応させる。メーカー表示のない接頭辞付き型番と、`RPI-` で始まる他メーカー（タカチ電機工業）の型番は接頭辞を残す。元の型番は `expectedModels` に残る。
- 商品名先頭の `【N】`（多くはスイッチサイエンスの商品番号）は探索のキーにしない。せんごく自社のケーブル・コネクタにも同じ形の番号があり、別製品を候補にしてしまうため。レビューでは、相手がスイッチサイエンスで番号が一致するときの補強証拠に限る。（0.6.4で、番号がスイッチサイエンスの商品番号と確かめられたメーカー表示に限って探索に使うよう変更した。下の0.6.4を参照）
- 候補が2,348組と多いため、メーカー別36バッチをClaude Sonnet 5.5が判定し、統合レビュー（Claude Opus 5.5）は全行を8分割で通読したうえで、既存の判定との矛盾（同じせんごく商品が、互いに別判定の2商品とそれぞれ同一になる組）を0件になるまで裁定した。統合レビューで変えた行は `reviewerModel` を Claude Opus 5.5 にし、初回判定とそのモデルを根拠文に残す。
- 統合レビューの裁定方針: 同じメーカー型番で定格・仕様の記載が店舗間で食い違うもの（1.5Aと1A等）は要確認。メーカーが別コードにした版違い（A145とA145-V033）と、偶然一致した短い数字は除外。片方の店舗の製造元名が商品名・型番と対応しない登録誤りは、もう片方の名称と型番が一致すれば同一商品にし、誤りを `missingEvidence` に記録する。既存の照合で公式ページ本文を確認済みの事実（題名と搭載モジュールの違い等）は、そのレビューを根拠文で名指しして使う。推移的な自動承認はしない。
- 相違点（`differences`）は利用者の画面にそのまま出るため、本体・販売条件の実際の違いだけを `項目: <products[0]の店>「値」 ↔ せんごく「値」` の形で書く。せんごくは常に `products[1]` で、パネルが商品ごとに左右を入れ替える。
- 製品群（類似商品）は従来どおり秋月/SSの組だけで生成し、せんごくの類似商品は出さない。全組で価格比較承認はなく、参考記録価格だけを表示する。

件数、要確認18組、統合レビューで変更した23組、範囲外は[店舗間の照合範囲](../roadmap/three-store-mapping.md#061-せんごくの追加2026-10-30判定)を参照。

## 0.6.3: 店舗固有の型番表記から作る探索キー、alias、全店舗の製品群

状態: 採用 / 2026-11-01 / Issue #45 / userscript 0.6.3

2026-11-01の監査で、型番が店舗固有の書き方で包まれているため、探索に出ない組が見つかった。

- せんごく `【…】` 付きの296行は、どの関係にも入っていなかった。
- ラズパイ基板では、せんごくを含む組が0/72だった。
- Seeed SKUでは、`SEEED-` 付きや連結SKUの3組と、秋月の旧い書き方（`SKU(旧部品番号)` 等）の12組が漏れていた。

### 導出キー

保存済みの `codes` と指紋は変えない。探索のときだけ、追加のキーを導出する（`derivedCodes`）。

| 対象 | 導出するキー |
|---|---|
| せんごく型番欄の `【N】rest` | Waveshare・LUCKFOX・Argonの3表示では括弧内の数字（メーカーSKU）。他の表示では括弧内はせんごくの通し番号なので使わない。 |
| せんごく型番欄の括弧の後ろ（rest） | 既存の接頭辞規則（`identityCodes`）を通したもの。メーカー表示が `Raspberry Pi` なら、restの中の `SC####` も使う。 |
| 型番欄の `SEEED-` + 9桁 | 9桁のSeeed SKU |
| 秋月の旧いSeeed行の型番（`104030003(LED05291P)`、`SKU-102010027`、`114020161/114020163`） | 括弧の前の9桁、`SKU-` の後の9桁、`/` で区切った各9桁。`+` で連結した組（`113991274+114992364`）はセットの可能性があるため導出せず、aliasで扱う |
| Raspberry Piの製造記号付き型番（`SC0194(9)`、`SC0130(J)`） | 括弧の前のコード |

導出キーの扱いは次のとおり。

- 0.6.1で探索のキーにしないと決めた商品名先頭の `【N】`（スイッチサイエンスの商品番号）とは別物で、その決定は0.6.3では維持した（0.6.4で一部のメーカー表示に限って変更）。
- 保存コードで見つかる組は、従来どおりそのコードだけを記録する。導出キーで初めて見つかる組だけを `derived` として候補一覧に印を付ける。
- `derived` の組のフィンガープリントは、2行のフィンガープリントに、組を見つけたキー（並べ替えた `codes`）を加えたもの。レビューはこのキーを根拠に書くため、aliasや導出規則を変えると、同じ2行がまた組になってもレビューのやり直しになる。保存コードの組のフィンガープリントは変えない。
- レビューの由来は `indexed derived code` と残る。
- 末尾の版・構成記号（`-V11` 等）は削らない。

### alias

型番欄に公式コードがない行（秋月のZero W、KSYの `RASPIZWHSC0065`、せんごくの `RPi4B-4GB` 等）には、`data/matching/aliases.json` で1行ずつ探索キーを付ける。

- 1つのaliasは、`key`、`fingerprint`、`codes`、20字以上の `evidence`、`reviewedAt` を持つ。
- 次の場合は生成が停止する。
  - 元行の変更
  - 既存コード・導出キーとの重複
  - 短すぎるコード
  - 同じ行への重複
  - 候補を1組も増やさないaliasコード。コードごとに、その行の組のうち、両行の保存コード・導出キーだけでは見つからない組を1つ以上作る必要がある。相手側のaliasでできた組に含まれるだけでは足りない。
- aliasは探索キーであって、同一性の判定ではない。組ごとのレビューを省かない。
- 0.5.1の「KSYの店舗独自コードに埋め込まれた製品番号は取り出さない」は一般規則として維持する。KSYの4行（Zero/Zero W/Zero WH/3B+）は、商品名が公式品を示すことを確認したaliasだけで扱う。

### 製品群

製品群の関係は、秋月/SSの組だけでなく、全店舗の組で作る。

- 向きは候補と同じく、カタログの店舗順に従う。
- 0.5.1・0.6.1の「KSY・せんごくの類似商品は出さない」は、この版で置き換える。
- 次の群を追加した。
  - Zeroシリーズ（5構成×4店）
  - XIAOのMCU別11群（標準/Pre-Soldered/Plus/Sense）
- Pico・Pi 4・Pi 5の群には、KSY・せんごくの本体を加えた。

### 規模と表示

- 類似商品は108組から823組に増え、実行時表のソースは約1.07MB増えた。
- パネルの他商品履歴の取得は、従来どおり1ページ最大8件・同時2件である。
- それ以降は `reference_only` で、通信は増えない。

- `userscript/core/relationTable.ts` が `packRelations` と `unpackRelations` を持つ。
  - 文字列は出現回数の多い順に1つの表へまとめる。
  - 商品は (店舗, ページ, variant) ごとに1回だけ持つ。
  - 対応の行は番号で文字列と商品を参照する。末尾の空欄は省く。

  - 戻した結果は従来の表と完全に一致する。商品オブジェクトも同じ5,273個を共有する。
  - パネル側のコードは変えていない。
  - 表が壊れていれば、読み込み時に例外を出す。版の違い、存在しない番号、未知の分類が対象。

- 往復はテストで固定した。
  - 実データでは、生成器の出力と配布表が一致する。
  - 任意の文字列でも往復する。`` ` ``、`${`、`\`、U+2028 を含む。
- 番号は再生成ごとに振り直すため、生成物の差分は読めない。確認は `data/matching` 側の差分と `matching:check` で行う。

## 0.6.4: 注記・メーカー接頭辞・再販表記の探索キーと、探索の段階

状態: 採用 / 2026-11-02 / Issue #48 / userscript 0.6.4

2026-11-02の監査で、全5店舗の全行（44,518行）を対象に、探索に出ない組を型番の書き方ごとに数えた。主な漏れは4種類だった。

- 型番の後ろの注文・製造の注記（東芝の `TC74HC138AP(F)`、JSTの `S2B-PH-K-S(LF)(SN)`、TIの `LMC660CN/NOPB`）と、`/` で並べた候補（`PIM185/PIM208`）
- スイッチサイエンスのメーカー接頭辞（`SFE-BOB-11083`、`ATMEL-ATMEGA328P-AU`、`DIGI-XB2B-WFPT-001`）
- せんごくがスイッチサイエンス品を再販するときの表記（`SSCI-012164/1216`、`【3650】M5Stack用プロトモジュール`）
- スイッチサイエンスの旧い行が、自店名をメーカー欄に書いた再販品（`M5STACK-K033`）。M5Stack公式との組が、メーカー不一致として落ちていた

### 導出キーの追加

`derivedCodes` に次を加えた。保存済みの `codes` と指紋は変えない。

| 対象 | 導出するキー |
|---|---|
| 型番の `(…)` の前、`/NOPB` の前 | その部分。英字と数字の両方を含む、ハイフン区切りの品番の形のものだけ（`No.13(3pcs)` は対象外） |
| `/` で区切った型番 | どの部分も5文字以上の品番の形なら、各部分。`PIC16F84A-20I/SS` のような短いパッケージ記号は製品の一部なので分けない |
| メーカー接頭辞 `SFE-`、`DFROBOT-`、`ADA-`、`POLOLU-`、`WAVESHARE-`、`PIMORONI-`、`ARDUINO-`、`FEETECH-`、`KITRONIK-`、`UCTRONICS-`、`DIGI-`、`ATMEL-`、`MICROCHIP-`、`M5STACK-`、`ALIENTEK-`、`BENEWAKE-` | 接頭辞の後ろの品番。メーカー欄ではなく接頭辞で判定する。数字だけの品番（`POLOLU-3424`、`ADA-4200`）はメーカーをまたいで偶然一致するため取り出さない |
| せんごく型番欄の `<code>/<4〜5桁>` | 前半の `<code>`（とその接頭辞を除いた品番） |

0.6.3の `SC0194(9)` の規則は、括弧の注記の規則に含まれる。

### 参照キーと探索の段階

せんごくの再販品は、スイッチサイエンスの商品番号を書いていることがある。

- 型番欄の `<code>/<番号>`
- 商品名・型番欄の `【番号】`

これを参照キー `SWITCH-SCIENCE/<番号>` とし、スイッチサイエンスの各行には自分の商品番号から同じ形のキーを作る（`referenceKeys`）。

0.6.1は、商品名先頭の `【N】` を探索キーにしないと決めていた。せんごく自社のケーブル・コネクタにも同じ形の番号があるためである。この版では、その誤りが起きないメーカー表示に限って使う。

- 2026-11-02の全行で、番号がスイッチサイエンスの商品番号として存在し、名前も対応したのは次の表示だった。
  - M5STACK: 420行中420行
  - スイッチサイエンス: 37行中37行
  - DFROBOT、Pololu、SONY (ソニー)、D-Robotics、DAMIAO、Arduino、ALIENTEK: 全行
- 次の表示とメーカー表示のない行は使わない。
  - Waveshare: 括弧内はメーカーSKU
  - ノンブランド、Raspberry Pi: せんごくの通し番号
  - メーカー表示なし: 130行中67行だけが対応した
- `<code>/<番号>` の形は、メーカー表示によらず使う。4〜5桁に限ったのは、`AMCS-473/630`（630 Vの耐圧）を除くためである。

探索は段階に分けた（`discover(left, right, ...tiers)`）。

1. 保存コード
2. 導出キーとalias
3. 参照キー

ある段階で見つかった組は、その段階のキーだけを記録する。後の段階は、それまでに見つからない組を加えるだけである。そのため、参照キーを加えても既存の `derived` の組のキーと指紋は変わらず、既存のレビュー3,842件はそのまま有効である。

### メーカー欄の自店名

スイッチサイエンスの行がメーカー欄に「スイッチサイエンス」と書いていても、メーカーの主張としては扱わない（`makerClaim`）。

- 探索のメーカー不一致の除外にだけ影響する。
- 保存コードと既存の導出キーでは、この除外で落ちていた組は0組だった。
- この版のメーカー接頭辞の規則で見つかる、M5Stack公式との組だけが新しく出る。

### 結果

- 新しい候補は245組だった。導出キーで220組、参照キーで25組が見つかった。
- 全組を個別に判定し、同一商品208・要確認15・除外22とした。
- 除外の多くは、色違い（12組）とランク違い（5組）である。注記の前の部分が一致して見つかったものを、判定で外した。キーは探す範囲を広げるだけで、同一性は判定で決める。
- 内訳と変更した判定は[店舗間の照合](../roadmap/three-store-mapping.md)の0.6.4を参照。

## 0.6.5: 名前ベースの候補探索

状態: 採用 / 2026-11-02 / Issue #49 / userscript 0.6.5

0.6.4までの探索は、型番から作るキーだけで組を作る。型番欄に有効な型番がない行は、商品名に製品の型番が書いてあっても組にならない。例:

- 秋月「タイマーIC NJM555D」（型番 `NJM555D`）と、せんごく「タイマーIC NJM555D」（型番欄が空）
- 秋月「トロイダルコア T-50-10」と、せんごく「ダストコア　T-50-10」（型番欄が空）

この版では、商品名から組を提案する。提案は候補ではない。判定したaliasを通して初めて候補になり、組ごとにレビューする。名前の近さで同一性を決めない（上の「背景と境界」）。

### 提案の作り方（`scripts/matching/names.ts`）

1. 商品名を正規化する（NFKC・大文字化）。店舗の注記を除く: `《お取り寄せ商品》`、`【取寄せ品】` 等の `【…】`、`[EOL]`、`--販売終了`、`--在庫限り`。
2. 英字と数字の両方を含む4文字以上の語を取り出す。`/` で並んだ語は、全体と各部分の両方を使う（`DHT12/BMP280/BMM150`）。
3. 量・数を表す語は除く: `5V`、`5V3A`、`3.3V`、`100MHZ`、`2X20`、`4-PIN`、`AWG22`、`V2.1`。`74HC595N` や `2N3904` は品番として残る。
4. 各行の自分のコード（保存コードと導出キー。aliasは含めない）も語に加える。名前が相手の型番を含む組を拾うためである。
5. 同じ語を持つ行どうしを組にする。20行を超える語は使わない。チップ名・規格名・シリーズ名で、1つの製品を指さないためである。
6. 次の組は除く。
   - 同じ店舗の組
   - メーカー欄が食い違う組。コード探索と同じ規則（`compatibleMakers`）で、スイッチサイエンスの自店名は主張として扱わない
   - 両方の行が自分のコードを持つ組。コード探索が組にしなかったことは、別製品の証拠になる（下の測定）
7. 名前の近さは、正規化した商品名の文字3-gramのDice係数で測る。
8. 各行について、相手店舗ごとに近い順の上位2組を残す。どちらかの行の上位2組に入れば残る。既に候補・製品群にある組も順位に含めるため、レビューした組が抜けても、次の組が繰り上がって提案されることはない。
9. 名前の近さが0.2未満の組は除く。最後に、既に候補か製品群にある組を除く。

計算量:

- 名前を読む: O(N·L)
- 語ごとの組作り: O(Σ min(df, 20)²) ≤ O(N·T·20)。Tは1行の語数
- 順位付け: 組数Pに対して O(P log P)

全行どうしの総当たりはしない。2026-11-02の44,518行では、語は52,615種、比較は29,805回で、この環境では約0.14秒だった。

### しきい値の測定

2026-11-02のカタログで、提案を2回標本抽出し、Claude Sonnet 5.5のサブエージェントが同一・類似・別製品・不明に分けた。

1回目は、両側の型番の有無を問わず、名前の近さ0.25以上の上位2組（2,041組）から、近さの帯ごとに15組、計90組を取った。

| 帯 | 同一 | 類似 | 別製品 | 不明 |
|---|---:|---:|---:|---:|
| 両側に型番がある87組 | 1 | 49 | 34 | 3 |
| 片側に型番がない3組 | 2 | 0 | 1 | 0 |

両側に型番がある組は、別の型番の別製品（Pi用CSIケーブルの `SC1128` と `SC1130` 等）か、同じチップを使う別製品が大半だった。そこで、片側に型番がない組に限った。

2回目は、片側に型番がない提案から80組を取った。

| 名前の近さ | 同一 | 類似 | 別製品 | 不明 |
|---|---:|---:|---:|---:|
| 0.3以上（15組） | 11 | 1 | 3 | 0 |
| 0.2〜0.3（15組） | 1 | 2 | 9 | 3 |
| 0.1〜0.2（15組） | 0 | 5 | 10 | 0 |
| 0.1未満（15組） | 0 | 0 | 15 | 0 |
| 21〜40行の語だけで見つかる組（20組） | 0 | 8 | 12 | 0 |

この結果から、名前の近さ0.2以上、語の行数20以下とした。上位2組の代わりに「互いに上位2組」とする案も試した。その案では、秋月「ショットキーバリアダイオード 60V1A 11EQS06」とせんごく「整流用ショットキーバリアダイオード 60V 1A　11EQS06」（近さ0.94、同一）が落ちたため、採らなかった。

### 提案から候補へ

提案は `npm run matching:names` が1行1組のJSONで出す。`coverage.json` の `nameProposals` には、まだ判定していない提案のIDが入る。

- 判定は、コードの候補と同じ4分類（同一商品・類似商品・要確認・対象外）で行う。
- 同一商品・要確認・対象外の組は、型番のない側の行にaliasを付けて候補にし、組ごとのレビューを残す。
  - 同一商品: 相手の行の自分のコードのうち、型番のない側の商品名に語として現れるもの（せんごくの商品名中の `104990172` 等）。なければ共通語になったもの。相手の型番を持つ他の行とも組になり、その組もレビューする。
  - M5Stack公式の行が相手の場合: 要確認でも、レビューで選んだvariantのコード。レビューはvariantをコードで指すためである。
  - それ以外（要確認、対象外、相手のコードが共通語にない同一商品）: 相手の行のページ参照キー。
- ページ参照キーは、各行が自分のページから作るキー（`AKIZUKI/104326`、`SENGOKU/EEHD-6WWU`）である。0.6.4のスイッチサイエンスの商品番号キーを全店舗に広げた（`pageReference`、`referenceKeys`）。行ごとに一意なので、それだけでは組を作らない。aliasが相手のページを指したときだけ、その1組ができる。追加後も、既存の候補4,087組のIDとキーは変わらない。
- 対象外の組も候補とレビューに残す。同じ組を次回また提案しないためである。
- 類似商品は、2行の製品群（`families.json`）にする。共通の用途、variant、相違点を表す特徴を持つ。レビューで対象外とすると、製品群の組も作られなくなる（対象外の同一性を類似商品に変えない規則）。そのため、類似商品の組はレビューに入れない。
- M5Stack公式のようにvariantを持つ行は、製品群でも `offerId` でvariantを1つ指す。variantのない行には `offerId` を書かない。どちらに反しても生成は止まる。レビューと同じく、どのvariantと比べたかを関係に残すためである。

### 探索の段階の順序

0.6.4の段階は「保存コード → 導出キーとalias → 参照キー」だった。この版で次の順にした（`discoveryTiers`）。

1. 保存コード
2. 導出キー
3. 参照キー（各行のページと、せんごくの再販番号）
4. alias

aliasは、行が自分のキーで見つけられない組を足すための探索キーである。2の段階に置くと、自分のキーで既に見つかる組の記録キーまで変えてしまう。例: せんごく「M5StickC Speaker Hat」（EEHD-5HEF）に、M5Stack公式のvariantコード `U055` のaliasを付けた。すると、再販番号 `SWITCH-SCIENCE/5754` で見つかっていたスイッチサイエンス5754との組が、先に `U055` で見つかった。その結果、組のキーと指紋が変わり、既存のレビュー4件が無効になった。

aliasを最後の段階にした後、既存の候補4,087組のIDと指紋はすべて変わらないことを確かめた。

### 統合確認の規則

Sonnetの判定107組を、Claude Opus 5.5が全件読んで確認した。次の規則で29組を変えた。変えた組の根拠には「初回判定（Claude Sonnet 5.5）は…」と元の判定を残す。

- 同一商品から要確認へ（10組）: 複数のメーカーが同じ名前で作る型番。片側のメーカーが不明なら、同じメーカーの製品とは決めない。
  - 対象: `1N4148`、`1N60`、鉄粉コアの `T-50-2` 等、`SK6812MINI`
  - `NJM555D`（日清紡）、`11EQS04`（日本インター）、`RWS100B-5`（TDKラムダ）のようにメーカー固有の型番は、片側のメーカー欄が空でも同一商品とした。0.6.4の `MCP3002-I/P` と同じ扱いである。
- 要確認から同一商品へ（1組）: `TLP624(F)` と `TLP624`。`(F)` は東芝の鉛フリー品の注文接尾辞で、0.6.4の `TC74HC00AP(F)` と同じ扱いである。
- 類似商品から対象外へ（4組）: 一方を他方の代わりに選べない組。
  - XT90のオスとメス（2組）: 互いに嵌合する相手側の部品である。
  - 別々のホスト専用のLoRa拡張ボード（2組）: SPRESENSE用とM5Stack用、SPRESENSE用とArduinoシールド。
  - 汎用の評価ボードとホスト専用ボードの組（秋月 `E220-900T22S(JP)-EV1` とSPRESENSE用）は、類似商品に残した。
- 類似商品の特徴（14組）: 「記載なし」を値から除き、具体的な相違だけを残した。同じ製品群の組には同じ名前を付けた（「MAX31855 熱電対アンプモジュール」「Raspberry Pi 3/2/B+用ケース」）。

旧対応表（`legacy.json`）で要確認だった1組（a106875-s1607、LS027B4DH01の評価キットと液晶モジュール）は、名前で提案されてレビューした。その結果、対象外とした。評価キットは液晶パネルを部品として含む別の商品だからである。レビューの根拠には、旧判定（gpt-5.6-lunaのinsufficient_evidence）を残した。

### 結果

- 名前の提案は107組だった。判定の内訳は次のとおり。
  - 同一商品: 28組
  - 類似商品: 18組
  - 要確認: 24組

## 0.6.6: 型番のある商品どうしの類似商品探索

状態: 採用 / 2026-11-02 / Issue #50 / userscript 0.6.6

0.6.5の名前探索は、片側に型番がない組だけを提案する。両側に自分の型番があり、型番が一致しない組は提案しない。こうした組は良くても類似商品だからである。一方で、同じ製品系列の版違い・構成違いは、型番の末尾だけが違う形でよく出る。例:

- M5Stack UnitV2: `U078-D`（標準カメラ）、`U078-M12`（M12レンズ版）、`U078-USB`（カメラなし）
- M5Stack CoreS3: `K128`、`K128-LITE`、`K128-SE`

0.6.3までの製品群は、こうした系列の一部（Pico、XIAO、Core2 等）だけを手で登録していた。この版では、両側に型番がある組から類似商品の候補を提案する。提案は製品群か除外の記録にだけ入り、レビュー（`reviews.json`）や同一商品にはならない。

### 範囲の測定

2026-11-02のカタログ（44,518行）で、0.6.5と同じ名前の語（20行以下）で組になる、両側に自分の型番がある他店舗の組を数えた。

- 組は8,108組だった。そのうち4,031組は、候補・関係・製品群に既にある。残りの4,077組が未照合である。
- 未照合の組を名前の近さ（文字3-gramのDice係数）で分けると、次のとおり。

| 名前の近さ | 組 |
|---|---:|
| 0.5以上 | 517 |
| 0.4〜0.5 | 402 |
| 0.3〜0.4 | 573 |
| 0.2〜0.3 | 924 |
| 0.2未満 | 1,661 |

- 店舗の組ごとに上位2組・近さ0.2以上に絞っても、2,040組残る。多い順に、スイッチサイエンス/せんごく 562、秋月/スイッチサイエンス 499、秋月/せんごく 358、スイッチサイエンス/公式 236、公式/せんごく 170。
- メーカー欄は、両側とも空か自店名の組が954組で最も多い。両側ともM5Stackの組は201組だった。

上位2組から名前の近さの帯ごとに18組、計90組を取り、Claude Sonnet 5.5のサブエージェントが同一・類似・別製品・不明に分けた。

| 名前の近さ | 同一 | 類似 | 別製品 | 不明 |
|---|---:|---:|---:|---:|
| 0.5以上 | 3 | 8 | 7 | 0 |
| 0.4〜0.5 | 1 | 14 | 3 | 0 |
| 0.3〜0.4 | 1 | 7 | 8 | 2 |
| 0.2〜0.3 | 1 | 8 | 8 | 1 |
| 0.2未満 | 0 | 5 | 13 | 0 |
| 計 | 6 | 42 | 39 | 3 |

類似の割合は帯ごとに28%〜78%で、名前の近さのしきい値では件数も精度も絞れない。一方、型番の語幹（下記）も共有する8組は、類似6・別製品2だった。語幹を共有しない82組は、類似36・別製品37・同一6・不明3だった。

### 提案の規則（`proposeSimilar`）

次の2つを両方満たす組だけを提案する。

1. 0.6.5と同じく、商品名の型番らしい語（または自分のコード）を共有し、その語を持つ行が20行以下である。他店舗の組で、メーカー欄が食い違わない。
2. 両方の行が自分のコード（保存コードと導出キー。aliasは含めない）を持ち、型番の語幹を共有する。語幹とは、コード自身と、`-` で区切った先頭部分のうち、英字と数字を含む4文字以上のもの（`AI-003-PRO` → `AI-003`、`AI-003-PRO`）である。英字を含まない先頭部分（書籍ISBNの `978-4-8222` 等）は使わない。

既に候補・関係・製品群にある組は提案しない。順位付けやしきい値は使わない。

計算量は、0.6.5の語ごとの組作り（O(N·L) + O(Σ min(df, 20)²)）に、組ごとの語幹の照合 O(C·K)（Cは1行のコード数、Kは区切りの数）を加えたものである。全行どうしの総当たりはしない。テストは2万行×2店舗で上限時間内に終わることを確かめる。

提案は `npm run matching:similar` が1行1組のJSONで出す。`coverage.json` の `similarProposals` には、まだ判定していない提案のIDが入る。

### 判定の記録

提案した組は、次のどちらかで記録する。

- 類似商品: `families.json` の製品群に、両方の行をメンバーとして入れる。製品群のメンバーは互いに比較できる必要がある。違う店舗で `variant` が違うメンバーの組は、すべて類似商品の関係になるからである。
- 除外: `dismissals.json` に1組1行で記録する。
  - `products`: 2行のキー。カタログの店舗順に並べる。
  - `fingerprint`: 両方の行のフィンガープリントから作る。候補と同じ式である。
  - `decision`: `different`（類似商品ではない）か `identity`（同一商品の可能性がある）。`identity` の組は、類似商品にはしない。同一かどうかは、aliasとレビューでしか決めない。
  - `evidence`（20文字以上）、`reviewedAt`、`reviewerModel`

除外は、現在の提案を指していなければならない。行が変わった（フィンガープリントが違う）除外、提案にない組（候補・関係・製品群の組を含む）を指す除外、重複した除外は、生成時にエラーになる。

### 判定の手順と統合確認

提案234組は、組でつながる行ごとに53グループ（224行）になった。グループ単位で、Claude Sonnet 5.5のサブエージェント4体が判定した。各グループで、製品群（ラベル・用途・メンバーごとの `variant` と特徴）か、組ごとの除外を返す。判定の規則は次のとおり。

- 製品群のメンバーは、同じ用途で互いの代わりに選べる製品に限る。例: 版・世代、センサー・レンズ、ヘッダーの有無、容量、測定レンジ、コイル電圧、付属品の有無。
- 次は別製品として除外する。
  - 部品と、それを載せたモジュール・評価ボード
  - 本体と、その付属品（ホイール、タイヤ等）
  - 嵌合する相手側の部品（XT90のオスとメス）
  - 別々のホスト専用の部品
- 特徴の値は、商品名・型番から読める具体的な値だけにする。「記載なし」「不明」は使わない。メーカーの型番そのもの（店舗の接頭辞を除いたもの）は、具体的な値として使ってよい。
- 店舗の別バリエーションを持つ行（M5Stack公式）は、該当するバリエーションを `offerId` で指す。
- 既に同一商品として照合済みの行どうしは、同じ `variant` と同じ特徴にする。
- 表記の違いだけで同一の可能性がある組（`LM336Z-5.0` と `LM336Z-5.0/NOPB`、片側の改版記号がない `FS90R` と `FS90R-V2` 等）は、`identity` として除外する。

Claude Opus 5.5が53グループの全行を読んで確認し、1グループを変えた。ATOMS3R（`C126`）は、初回判定では4つの構成を1つの製品群にしていた。これを、カメラキット（`C126-CAM`、`C126-M12`）と、本体・プロトキット（`C126`、`C126-EXT`）の2群に分けた。カメラキットと液晶付き本体は、ATOMS3R本体が共通でも主な用途が違うからである。2群の間の20組は別製品として除外し、根拠に「初回判定（Claude Sonnet 5.5）は…」と元の判定を残した。初回判定の全文は `.claude/goal-loop/similar-families-066/` に置いた。

また、同じ系列の2つの版を両店舗が売る場合（INA226ユニットの `U200` と `U200-1A` 等）、同じ版どうしの組は既に同一商品の候補なので、提案は互いにつながらない2組に分かれる。初回判定はグループごとに同じラベルの製品群を2つ作った。統合側は、`U200`・`K041`・`K129` の3系列で、これを1つの製品群にまとめた。製品群の中で同じ `variant` の組は関係を作らないので、関係は変わらない。

### 結果

## 0.6.7: 型番の語幹だけを共有する組の類似商品探索と、保留した同一性の確認

状態: 採用 / 2026-11-02 / Issue #51・#52 / userscript 0.6.7

0.6.6の提案は、商品名の語と型番の語幹を両方共有する組に限った。M5Stackの版違いには、名前に共通の語がない組が多い。例: CardKB `U035`（「カード型キーボードユニット」）と `U035-B`（「CardKB Mini」）。この版では、片方の型番がそのまま語幹である組を、名前の語がなくても提案する（#51）。また、0.6.6で同一の可能性として除外した13組を、aliasとレビューで確認した（#52）。

### 範囲の測定

0.6.6の時点で、型番の語幹を共有するが、20行以下の名前の語を共有しない他店舗の組は2,372組だった。組ごとに、共有する最長の語幹を代表として数えた（0.6.6の「`ESP32` 271組」は、語幹ごとに重ねて数えた値）。

| 店舗の組 | 組 |

| 秋月 / せんごく | 871 |
| SS / せんごく | 528 |
| SS / M5Stack公式 | 386 |
| 秋月 / SS | 275 |
| M5Stack公式 / せんごく | 205 |
| 秋月 / M5Stack公式 | 63 |
| KSY と他店 | 44 |

- メーカー欄は、両側とも空か自店名が1,285組、片側だけが651組、両側ともM5Stackが436組だった。
- 代表語幹の多い順: `ESP32` 250組、`Y2KB` 220組、`K016` 126組、`S007` 97組、`XB-3` 90組。
- 組の形で分けた。「基本型番」は、片方の型番が語幹そのもの（`U035` と `U035-B`）の組。「兄弟」は、両方が語幹を延ばした型番（`MK-617-5` と `MK-617-6`）の組。語幹の行数ごとの組の数は次のとおり。

| 層 | 標本 | 類似 | 別製品 |
|---|---:|---:|---:|
| 基本型番・5以下 | 12 | 11 | 1 |
| 基本型番・6〜10 | 12 | 12 | 0 |
| 基本型番・11〜20 | 12 | 7 | 5 |
| 兄弟・5以下 | 12 | 5 | 7 |

| 兄弟・11〜20 | 12 | 11 | 1 |
| 兄弟・21以上 | 18 | 6 | 12 |

基本型番で語幹の行数が10以下の層は、24組中23組が類似だった。11〜20行では12組中7組に下がる。`C008` がATOM Lite・Matrix・Voiceを、`U078` がUnitVとUnitV2をまとめるように、行数の多い語幹は製品系列ではなく製品の範囲を指すからである。兄弟の組は、行数が少なくても色・サイズ違いの部品（嵌合する相手側を含む）が混じり、層ごとの割合が揃わない。標本の「類似」には、全件の判定で同一の可能性に分けた組（`MP-121M` と `MP-121M-1` 等）も含む。

### 提案の規則（`proposeSimilar` の2段目）

0.6.6の提案に、次の組を加える。

1. 両方の行が自分のコードを持ち、型番の語幹を共有する。他店舗の組で、メーカー欄が食い違わない。
2. 片方の行の自分のコードが、その語幹そのものである。
3. その語幹を持つ行が10行以下である（`SIMILAR_DISCOVERY.maxStemListings`）。

兄弟の組には、0.6.6と同じく名前の語の共有を求める。既に候補・関係・製品群にある組は提案しない。名前の語を共有しないので、提案の `tokens` は空になる。

計算量は、0.6.6の分（語ごとの組作り）に、行ごとの語幹の列挙 O(N·C·K) と、語幹ごとのブロック内の組作り O(Σ min(df, 10)²) を加えたものである。10行を超えるブロックは、組を作る前に飛ばす。組ごとの語幹の照合は O(C·K) である。全行どうしの総当たりはしない。テストは2万行×2店舗（2万組の提案）で3秒以内に終わることを確かめる。

この規則での提案は478組だった（代表語幹で数えた基本型番・10行以下の476組とほぼ一致する。差の2組は、短い方の語幹で条件を満たす組）。

### 判定の手順と統合確認

478組を、組でつながる行ごとに148グループ（571行）に分けた。Claude Sonnet 5.5のサブエージェント8体が、0.6.6と同じ形で判定した。各グループで、新しい製品群、既存の製品群への追加（`extensions`）、組ごとの除外を返す。判定の規則は0.6.6に次を加えた。

- 末尾の意味を項目から読めない組は `identity` として除外する。例: `-1`、`-3.4`、`-T`、`-D27Z`、hFEランクの `-O`・`-Y`・`-GR`。基本型番側が版を書いていない組も同じ。
- 末尾が版・構成を示し、名前や他の項目がそれを裏付ける組は、別製品として類似か別製品かを決める。例: `-V11`、`-V13`、`-B`、`-AWS`、レンズ、容量。
- 既存の製品群のメンバーと同一商品として照合済みの行は、そのメンバーの `variant` と特徴をそのまま使って追加する。

初回判定は、新しい製品群80件（358行）、既存の製品群への追加31行、別製品32組、同一の可能性61組だった。機械検査（`check067.cjs`）は、提案ごとにちょうど1回の記録、offer ID、特徴のキーの一致、「記載なし」「不明」等の禁止語、同一商品どうしの `variant` の一致を確かめた。

Claude Opus 5.5が148グループの全行を読み、22グループを変えた（2グループを1つにまとめた7件を含め、15件の差し替え）。

- メーカーが別SKUで売る基本型番と版付き型番は、同一の可能性ではなく版違いの製品群にした。メーカーSKUそのものの基本型番とは、M5Stack公式の型番か、メーカー型番と同じ店舗の型番である。
  - Faces用パネル: `A003` と `A003-V3`、`A004` と `A004-V3`
  - FIRE: `K007`、`K007-V26`、`K007-V27`
  - pHセンサーキット: `SEN0161` と `SEN0161-V2`
  - サーボ: `A076`（SG90 Servo）、`A076-B`（Servo Kit 180°）、`A076-C`（Servo Kit 360°）
  - この変更で、同一の可能性は61組から49組になった。
- 1つの製品系列が2つのグループに分かれ、特徴の名前や値の書き方が違っていた7系列を、1つの製品群にまとめた。対象は `A003`、`A004`、`A035`、`A088`、`A093`、`A146`、`K038`。例: LED数の「30LEDs」と「30」。
- 特徴を、項目から読める事実だけにした。
  - `S6775` と `S6775-01`、`M138` と `M138-V11` は型番だけにした。片側の名前だけの記載や、版をチップ名として書いた値を外した。
  - ジョイスティックの `ATMEGA8A` は、M5Stack公式の品名どおり `MEGA8A` にした。
  - バナナプラグ `P-416` 系の製品群名から、どの項目にもないメーカー名を外した。
- 0.6.6の製品群 `stem-a090` は「電力モニター付き」のv1.1・v1.2だけだった。この版で初代 `A090`（STM32F030）を加えた。その際、初回判定の「非搭載」は記載がないことからの推測なので使わず、製品群全体の特徴を「型番」と名前に書かれた「構成」に揃えた。ラベルは「ATOMIC Motion ベース」に変えた。

除外の根拠文は、初回判定を変えなかったものだけである。そのため、除外の `reviewerModel` はすべて Claude Sonnet 5.5 である。Opusの変更は、初回判定と理由とともに `.claude/goal-loop/stem-families-067/` に置いた。

## 0.6.8: 0.6.7で保留した同一の可能性49組の確認

状態: 採用 / 2026-11-02 / Issue #53 / userscript 0.6.8

0.6.7の語幹探索（#51）は、末尾の記号の意味が項目から読めない49組を、同一の可能性（`identity`）として類似商品から除外した。#52と同じ手順で、すべての組を決着させた。

### 判定の手順

- 統合側（Claude Opus 5.5）が、49組の両方の行の全項目を読んだ。同じ店舗が両方の型番を別の商品として売っているかも調べた。

- それ以外の組には、末尾付きの型番の行に基本型番のaliasを付けた（41件）。これで候補を作り、要確認のレビューを書いた（43組）。aliasはどれも、狙った組以外の候補を作らないことを事前に確かめた。
- 同じ製品の別表記と言える組はなかった。そのため、同一商品にした組はない。
- 決着した49組の `identity` は、すべて `dismissals.json` から外した。残る除外は `different` の65組だけである。

## 0.7.10: Pimoroniの追加

状態: 採用 / 2026-11-10 / Issue #94 / userscript 0.7.10

6店舗目のPimoroni（GBP、2026-11-09の日次収集の2,854商品・3,789バリエーション）を、既存の手順（`--import-store`、全店舗ペアの探索、組ごとのレビュー）で対応表に加えた。判定の中身と件数は[店舗間の照合範囲](../roadmap/three-store-mapping.md#0710-pimoroniの追加2026-11-10判定)に置く。ここには、規則として決めたことと、その理由を書く。

### 決定

1. **Pimoroniの行は店舗のvendor表記を残し、メーカーとして扱わない。** vendor表記は「Generic」「Raspberry Pi」「Sparkfun」のような店舗側のラベルで、メーカー名ではない。メーカーとして扱うと、相手の行がメーカーを別の名前で書く組が候補から落ちる。計測では108候補が落ち、そのうち85組はスイッチサイエンスの「Raspberry Pi Trading」とラベル「Raspberry Pi」の組だった（`~/tmp/pimoroni-94/work/maker-field.md`）。
2. **メーカー表記の3つの形は、Pimoroniの行だけに、vendor表記とSKUの形の両方が合うときに適用する。** Adafruit（`ADA<数字>` → `ADA-<数字>`）、Pololu（`POL-<数字>` → `POLOLU-<数字>`）、Kitronik（`KIT-<数字で始まる列>` → `KITRONIK-<残り>`、`-V2` のような末尾は残す）。他店の行は、メーカー欄から同じ形のキーを作っているので、ここで出会う。保存済みのコードは変えない。数字だけの値はキーにしない。他店の素のAdafruit・Pololuの番号は、メーカー名を持たない行（秋月）では `ADA-`・`POLOLU-` にならないので、つないでいない（範囲外として記録した）。
3. **バリエーションを持つ行のレビューは、そのバリエーション自身のキーが候補のコードに合うものを指さなければならない。導出キーも数える（`catalogs.ts` の `variantCodes`）。** #94より前は、バリエーションの保存済みSKUだけを数えていた。そのため、メーカー表記の形で見つかった候補（SKU `ADA2030` に対する `ADA-2030`）は、レビューを書けなかった（「reviewed variant must match candidate code」）。保存済みSKUだけを緩めて受け入れる代わりに、バリエーションのキーの集合を検査の対象にした。別のバリエーションを指すレビューや、キーが合わないバリエーションを指すレビューは、これまでどおり拒否する（`tests/unit/matching-generator.test.ts` が、Adafruit・Pololu・Kitronikの受け入れと、合わないバリエーション・商品にないバリエーションの拒否を固定している）。
4. **レビューは、保存した行だけで判定し、店舗のページは開かない。** コードと導出キーが見つけた1,705組を最大120組ずつ15バッチに分け、バッチごとに1人のレビュアー（Claude Sonnet 5.5）が書面の指示で判定した。残りの13組（名前の提案4組と同一性の可能性の9組）は統合側が判定した。各バッチは機械で検査し（ID、バリエーションの選択、必須項目、両方の行を名指す根拠）、統合側（Claude Fable 5.2）が、要確認の全組、疑問や注記のある全組、名称に共通の語がない同一商品の全組、数字の食い違う組、構造上の印の付いた組、印も注記もない組の固定乱数の標本60組を通読した。
5. **片方だけが書く情報の扱いは、先例の規則に合わせる。** 両側が同じメーカー製品番号を持ち、名称が製品について一致しているとき、端子・版・色・刻印を片方だけが書いていても、それは情報不足であって相違の証明ではない。`missingEvidence` に記録して同一商品にする。両側が違うことを書くとき、名称が製品について一致しないとき、コードの末尾が片方にないときは要確認のまま残す。初回判定が要確認とした23組をこの規則で同一商品にし、根拠に初回判定を残した。理由は、同じ種類の組を、以前のレビュー（`ADA-904` の `STEMMA QT`、`SC0130(J)`）と違う扱いにしないため。
6. **共有キーがaliasに由来する組の冒頭の1文は、機械的に書き換えた。** レビュアーはキーの由来を推測して書いていた。由来は対応表のデータから決まるので、23組の冒頭を、確認済みのaliasとして付けたコードと、同店の型番欄を挙げる形に統一した。判定・他の文は変えていない。
7. **類似商品の提案は、次のように記録した。**
   - 既存の製品群のメンバーと同一商品のPimoroniの行は、そのメンバーと同じ `variant`・同じ特徴・そのバリエーションの `offerId` で、同じ製品群に加えた（15行、15群）。
   - 行からは決められない同一性の可能性（HUSKYLENS `SEN0305` と `SEN0305-S` 等の9組）は、類似商品にも同一商品にもせず、他店の行に、Pimoroniのバリエーションのコードをaliasとして付けて候補にし、要確認で記録した。0.6.8と同じ扱い。
   - 別製品と分かる組は `dismissals.json` に除外として残した（4組）。
   - 店舗が違いバリエーションも違うメンバーが同じ群に入るには、同じ特徴キーが要る（生成器の規則）。型番の特徴が揃わない2つの新しい群は、特徴に「型番」と「製品名」を使った。
8. **名前の提案4組は却下した。** ADR-0018の0.6.5の記録方法（相手の行のページ参照を付けたalias、却下のレビュー）に従った。

### 価格

PimoroniはGBPで、税の扱いは不明。Pimoroniとの組で価格比較を承認したものはない（`pricePolicy` はすべて `null`）。表示は[ADR-0017](0017-cross-store-comparisons.md)と[ADR-0022](0022-yen-reference-from-daily-exchange-rate.md)のままで、Pimoroniの行は円の参考値を見出しにして記録価格を併記し、円の店舗の後に並べる。差額と「最安」の印は付かない。

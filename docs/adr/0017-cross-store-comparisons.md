# ADR-0017: 店舗横断の対応表と価格比較承認を分離する

状態: 採用 / 2026-09-07 / Issue #4 / userscript 0.4.0

追記: 初回80組の範囲は当時の記録。0.4.1以降の生成元・追加取得総数の上限・更新手順は [ADR-0018](0018-reviewed-catalog-mapping-pipeline.md) が拡張する。商品同一性と価格承認の分離は引き続き有効。

追記 (0.6.3 / Issue #46): 類似商品カードは対応1件ごとではなく、製品の種類ごとに1枚にした。同じ製品群 (`similarity.family`) に属し、閲覧中 → 他店の向きにそろえた差分が一致する対応を1枚にまとめる。カードには代表名と差分を1回だけ出し、店舗ごとの行に商品リンク・参考記録価格・照合根拠を置く。製品群の距離がない対応と差分のない対応は、従来どおり1件で1枚。並び順、取得上限 (`relatedEntries`)、各行の `data-relation-id` は変えない。見出しは、まとめた場合だけ「類似商品 (21件・7種類)」の形にする。取得上限を超えて価格を読み込まない行には、行ごとの説明を出さない。その理由はカードの注記で1回だけ示し、行には商品リンクと根拠を残す。対応表の配布形式は [ADR-0018](0018-reviewed-catalog-mapping-pipeline.md#規模と表示) を参照。

追記 (0.6.9 / Issue #55): 店舗の数が増え、1商品に照合済みの同一商品が4行以上つく商品が出てきた (2026-11-03 の対応表で23商品、最大10行)。そこで、同一商品の行の並び順と表示件数を決めた。順位を決める純関数は店舗名を知らない `userscript/core/relations.ts` の `orderStorePrices` に置き、`userscript/ui/related.ts` は並んだ結果を描くだけにする。
- 閲覧中の店舗は今までどおり先頭に固定し、並べ替えの対象にしない。
- 他店の行の並び順は、次の順に決める。
  1. 記録価格が円の店舗が先。円以外の通貨の店舗は送料・関税・税が入っていないので、円換算しても円の店舗とは順位を比べず、後ろにまとめて「送料・関税別」と書く。
  2. 最後に観測した在庫が、在庫あり・在庫僅少 → 入荷待ち・準備中・在庫確認中・不明・表示なし → 在庫なし・販売終了 → 最新の観測で未掲載、の順。
  3. 記録価格の安い順。
  4. 最終観測の新しい順。
  5. それでも同じなら、元の並び順 (`relatedEntries`) を保つ。
  
  履歴をまだ読み込んでいない行(読み込み中・取得上限外・取得失敗)は末尾に置く。そのため読み込み中は順番が動くが、全部の読み込みが終われば順番は動かない。
- 先頭3行 (`VISIBLE_STORE_PRICES`) を表示し、残りは「他の店舗（N件）」の折りたたみに入れる。開閉の状態は `data-state-key="store-prices-more"` で再描画後も保つ。2行以上あるときは、並び順の説明を1行だけ添える。
- 「最安」の印は、価格比較の承認 (`pricePolicy`) が通っていて、最後に観測した在庫が在庫あり・在庫僅少の行のうち、記録価格がいちばん低い行だけに付ける (`cheapestComparable`)。その価格が閲覧中の店舗より高ければ印は付けない。閲覧中の店舗の更新確認ができないときも付けない。承認のない行は並べ替えるだけで、最安とは言わない。2026-11-03 時点で承認は2組だけなので、印はほとんど出ない。
- グラフは常に「店舗別の記録価格」より先に置く。0.4.0〜0.6.8 は狭い幅のとき記録価格をグラフの上へ移していた。そのため、パネルの幅が店舗のレイアウトで決まる店舗（M5Stack公式の左カラム等）や画面幅によって順序が変わっていた。
  - 0.7.4 からは、どの幅でもグラフをパネルの幅いっぱいに置き、記録価格と統計をその下に置く。グラフの横に記録価格を並べる配置はやめた。
  - グラフの下は、店舗ではなく幅で分ける。閲覧中の店舗のカードを先頭に、他店のカードを同じグリッドに並べる。1枚 200px 以上で入るだけの列に折り返すので、広い欄では閲覧中と他店が横に並び、狭い欄では縦に積まれる。閲覧中のカードには最終観測と在庫を書き、統計は従来どおり折りたたみに入れる。
  - 他店の対応がない商品は、パネルの内側の幅が 560px 以上のとき、現在の記録価格の右に統計を置く。コンテナクエリのない Chrome 102〜104 では統計は価格の下に残る。
  - 0.7.3 までは、パネルの内側の幅が 700px を超えると横並びにしていた。そのため、スイッチサイエンスの 776px の欄では、グラフが幅の半分ほどに縮んでいた(#71)。幅のしきい値を 960px、800px と上げる案も試したが、店舗の欄の幅ごとに配置が変わるので、オーナーの判断(2026-11-04)で横並びをやめ、常に下へ置くことにした。
  - グラフの viewBox の幅は箱の幅に合わせ、上限 `CHART_SIZE.width` を 1,200px にした。計った中でいちばん広い欄(Pimoroni、1,091px)より大きいので、広い欄でも軸の文字は 12px のまま拡大されない。
- 並び順は観測した記録の順であり、今の価格や在庫を保証しない。販売単位の違い (1個とリール500個等) は承認のない行では確かめていない。そのため、まとめ売りの行は単価で比べず、表示価格のまま並ぶ。取得の順番・上限・回数は変えていない。

追記 (Issue #95): 類似商品・同一商品候補・要確認候補のカードは、店舗別の記録価格と同じ折り返しグリッド(同じ列規則)に並べ、各グループで近い順の上位3枚 (`VISIBLE_RELATED_CARDS`) だけを表示し、残りは「他の類似商品(N種類)」などの折りたたみにした。折りたたんだカードも文書内に残り、リンクと照合根拠は変わらない。並び順、同一差分のカードの統合、履歴の自動取得の上限 (`MAX_RELATED_HISTORY_LOADS`) は変えていない。幅が狭いパネルでは価格比較と同じく1列に積む。

## 背景と境界

店舗をまたいで同じ製品を探し、仕様違いの近い製品も区別して見たい。一方、似た商品名・同じ型番・近い価格だけでは、同一製品や同じ販売数量を証明できない。ADR-0001 の店舗内 ID と履歴 DB は変更せず、ユーザースクリプトに明示的な対応表を加える。店舗間で履歴をマージしない。

## 決定

- `userscript/adapters/productRelations.ts`: 店舗固有の対応表・表示名・元データ日時・根拠・不足情報・元のモデル判定を保持。実価格は埋め込まない。
- `userscript/core/relations.ts`: 店舗名を知らない索引、商品情報の一致確認、価格比較可否。対応表を O(R) で一度索引化し、閲覧商品に対して O(1 + 対応件数) で検索する。店舗カタログ同士の直積は実行しない。
- `same_product` と `reviewStatus` を分離。型番の暫定一致は候補であり、確定した同一商品と表示しない。`similar_product` は共通用途・差分を記録し、互換性を保証しない。情報不足は `unresolved`。対象外は配信しない。
- `pricePolicy` は独立した承認。税込通常販売価格、通貨、販売単位、付属品、リビジョン、対象 offer ID を確認した組だけ差額と重ね合わせを許可。送料・数量割引・販売店独自保証は含めない。`null` の単位もページの包装数量を確認したうえで明示的に承認する必要がある。
- 現行公開データの名前・型番が確認済み表記と異なる、疑わしい商品情報履歴がある、複数 offer、別価格種別、単位・税の不一致、未掲載、古いキャッシュ、版不一致なら参考表示へ降格。最新観測が条件確認から 90 日を超えた場合も再確認まで差額を止める。価格範囲は帯で表せるが確定差額を計算しない。
- UI は既存テーマ・Shadow DOM・DOM 生成 API を使用。確定同一商品の記録価格を右側へ、候補と要確認を折りたたみへ、類似商品を差分付きの別カードへ配置。色と線種で区別し、チェックボックスで系列を選択。グラフは各店の観測期間内だけで描画し、1 観測だけなら点を表示する。他店の観測終了から現在まで線を延長しない。観測日時と「現在の最安価格ではない」を明示する。
- controller だけが追加取得を所有し、閲覧商品を先に、他店は重複排除した最大 2 件同時で取得。描画・テーマ変更・価格種別変更は取得を開始しない。DataClient は商品・manifest の進行中要求を共有し、失敗は終端状態へ移す。429 の自動再試行なし。パネル破棄時に遅延描画 observer を切断する。LRU 索引更新は直列化して同時取得による取りこぼしを防ぐ。

## 更新・検証手順

1. 元商品 ID / URL / メーカー / 型番 / 名前を突合し、分類・根拠・差分・不足情報・取得日時・確認日を更新する。現行コレクターの型番欄は旧保存カタログのメーカー型番とは異なる場合がある。実際の公開 JSON を読み、確認した表記だけ `expectedModels` / `expectedNames` に足す。
2. 差額を許可するなら両店の商品ページで販売条件を確認し、公開 JSON の offer ID と単位を固定する。型番一致から承認を推論しない。構成差や情報不足を残したまま承認しない。
3. Verify: `node node_modules/vitest/vitest.mjs run tests/userscript --maxWorkers 2`。Expect: 全件成功。対応表の重複、M5Stack の対象 20 商品、双方向性、失敗時の参考表示、独立した系列終端、フォーカス保持、最大同時取得数を確認。
4. Verify: `npm run typecheck`、`npm test`、`npm run build:userscript`、`npm audit --audit-level=high` と CI の保存ページ E2E。Expect: 全成功、共通コアに店舗名なし、バンドルに HTML 文字列シンク/CDN なし。ブラウザでライト/ダーク、折りたたみ、系列切替、狭幅表示を確認する。テスト後は runner が残存していないことを確認。
5. userscript と package/lockfile の版を上げ、CI 成功後に `crawl-publish.yml` を `republish=true` で実行する。Verify: 公開バンドルの版・バイト列・両店 manifest・state を取得。Expect: 検証済みバンドルと一致し、再クロールせず観測回数とデータ版を維持する。

対応表だけを更新しても、インストール済みの旧 userscript には届かない。版の上昇と Pages の公開確認が必要。

# ADR-0008: 一覧ページは DOM ライブラリでなく正規表現で読み、保存済みページで検証する

- 状態: 採用(2026-09-06)
- 関連: `src/collectors/akizuki/listingParser.ts`、`tests/fixtures/akizuki/html/`、`tests/property/listing-parser.property.test.ts`

## 背景

秋月の一覧ページはサーバー側で描画された規則的な HTML で、BEM のクラス名(`block-cart-i--*`)が安定している。DOM パーサー(jsdom、cheerio)は依存とサプライチェーンの面積を増やし、数百ページの解析にはオーバースペック。

ただし一覧のレイアウトは 1 種類ではない。ほとんどのページは商品カード(`dl.block-cart-i--goods`)だが、ヒートシンク・ねじ・アンテナ・電池ボックス・駆動キットなど数カテゴリは並べ替え可能な仕様表(`table.block-goods-list-l--table`)で描画される。手書きのジャンル一覧を巡回していた頃はカードしか踏まなかったため、この差は表に出なかった(ADR-0012)。

## 決定

- パーサーは HTML 文字列に対する純粋関数。商品ブロックをクラス名で切り出し、各フィールドはアンカー付きの正規表現で読む。
- **2 つのレイアウトを 1 つの `ItemLayout` 記述で扱う。** ページに商品カードがなく仕様表がある場合だけ表として読む。表には**カートが存在しない**ため、購入可否は `false` ではなく `null`(不明)として扱い、在庫バッジだけで可用性を判定する。ここで `false` を捏造すると「在庫あり」の商品が `out_of_stock` として履歴に残る。
- 構造の前提が崩れたら `ListingParseError` を投げ、商品単位の軽微な問題は `issues` に積む。Collector はどちらも run の `complete` 判定に使う(ADR-0004)。
- 「N 件あります」の件数、ページャーの最終ページ、次ページのパスも読み、ページ数の整合性を run の完全性に含める。
- テストは**保存済みの実ページ**(gzip)に対する例示テストと、生成した HTML に対するプロパティテスト(壊れた入力で例外以外の異常終了をしない、抽出件数がブロック数を超えない)。

## 理由

依存ゼロで高速、失敗の仕方が明示的。ページ構造が変わったときは「静かに 0 件」ではなく「完全性エラー」になる。

## 結果

- サイトの改修時はフィクスチャを更新してパーサーを直す。フィクスチャの更新は手動で行い(`scripts/make-html-fixture.ts`)、ライブサイトへのアクセスはテストで行わない。
- プロパティテストは両レイアウトを生成する。カードだけを生成していたことが、表形式を数か月見落とした原因だった。
- Phase 2 / 3 の店舗が API(Shopify の `products.json`)を持つ場合、この決定は適用されない(Collector は店舗別)。

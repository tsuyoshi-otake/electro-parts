# ADR-0027: スイッチサイエンスと M5Stack 公式の在庫数を商品ページから読む

状態: 採用 / 2026-11-04 / Issue #74 / 契約 1.2.0 / userscript・拡張 0.7.5

ADR-0026 は、取得済みのデータに数が無い店舗の在庫数を記録しないと決め、商品ページを 1 件ずつ読むかどうかをオーナーの判断に残した。オーナーは 2026-11-04 に、M5Stack 公式とスイッチサイエンスの在庫数も記録すると決めた(「だめだよ、記録してよ」→ 方針の承認「その方針で進めて」)。この ADR は、読む範囲、相手の負荷とジョブ時間の上限、読めなかったときの記録、「100+」の扱いを決める。ADR-0014 の「商品ページの HTML は収集に使わない」は、在庫数に限ってこの ADR で改める。

## 調べたこと(2026-11-04、各店の商品ページ 1〜2 件と一覧 1 件)

| | M5Stack 公式 | スイッチサイエンス |
|---|---|---|
| 数のある場所 | 商品ページ。ページの表示は「10+ In Stock」のような段階。数はスクリプトの `_SIConfig.product.variants[i]['inventory_quantity'] = N;` と、バリエーションの `<option data-inventory="N">` にある | 商品ページの `<p>在庫数: 9</p>`。100 以上は `<p>在庫数: 100+</p>` だけ |
| 一括カタログ・一覧 | 数は無い(`available` の真偽値だけ、ADR-0014) | 同じ |
| 必要なリクエスト | 1 商品 1 件、664 件 | 1 商品 1 件。全商品なら約 10,382 件 |
| `robots.txt` | `/products/` を禁止していない | 同じ |
| 利用規約 | 「spider, crawl, or scrape」の禁止条項がある(ADR-0025) | この条項は無い |

## 決定

### オーナーの規約判断

- M5Stack 公式の規約の「spider, crawl, or scrape」の条項に、664 商品ページの取得が当たることを伝えたうえで、オーナー(このプロジェクトの持ち主)が 2026-11-04 に記録すると決めた。公開カタログに加えて公開の商品ページを読み、在庫数という事実だけを記録する。規約の解釈のリスクは残る。
- 丁寧さの規則(ADR-0009)はそのまま守る。同じ UA、前のリクエストの開始から 1.5 秒 + 0〜0.75 秒の間隔、`Retry-After` の尊重、1 回の実行のリクエスト上限。

### 読む範囲と上限

設定は `config/<store>.json` の `productPages` と `maxRequests`。

| | M5Stack 公式 | スイッチサイエンス |
|---|---|---|
| 対象 | 全商品(全バリエーションの数が 1 ページにある) | 在庫あり、かつバリエーション 1 つの商品だけ(2026-08 のスナップショットでは全商品がバリエーション 1 つ)。題名が「《お取り寄せ商品》」で始まる商品は除く(数の行が無い、下の追記) |
| 分割(`shards`) | 1(観測日ごとに全商品) | 4(観測日ごとに 1 組) |
| 1 商品の更新間隔 | 観測日ごと(#82 以降は毎日。それ以前は約 2 日) | 4 観測日ごと(#82 以降は約 4 日。それ以前は約 8 日) |
| 1 回の上限 | `maxPages` 900、`maxMinutes` 35、`maxFailures` 30、`maxRequests` 1000、`maxWaitMs` 300000 | `maxPages` 1800、`maxMinutes` 55、`maxFailures` 50、`maxRequests` 2100 |
| 見込み時間 | 664 件 × 平均約 1.9 秒 ≈ 21 分 | 在庫ありは約 5,800 件(在庫なし 43.8%、2026-08-02)。1 組 約 1,460 件 ≈ 46 分 |

- 全店舗は 1 つのジョブで順に動き、上限は 240 分。2026-11-01 の実測は計 116 分(秋月 90 分、せんごく 23 分)。追加の約 67 分を足して約 183 分になる。`maxMinutes` は、店舗が遅いときにもジョブ全体の上限を超えないための打ち切りである。
- スイッチサイエンスを全商品・5 分割(当初案)にしなかったのは、1 回約 65 分でジョブの余裕が 30 分を切るため。在庫なしの商品はカタログの `available: false` で買えないことが分かっていて、ページを読んでも数は増えない。
- 組の選び方: 観測日の番号(`observationDayCount`、基準 2026-09-10T20:00Z = 05:00 JST、1 日で 1 つ進む。#82 より前は 2 日で 1 つ進む `observationRound` だった)を `shards` で割った余りの組を読む。商品の組は handle の FNV-1a で固定し、組の中の順番は回ごとに変える。`maxPages` や時間で打ち切っても、同じ商品ばかり読み残さない。

### 止める条件

- 429 を受けたら、その店舗の商品ページはそれ以上読まない(フェッチャー自身の再試行の後)。フェッチャーは `Retry-After` を `maxWaitMs`(既定 120 秒)まで待って再試行し、それより長い指示を受けたら待たずに止まる。
- 404・410 以外の取得失敗が 3 回続いたら止める。404・410(カタログ取得後に消えた商品)は失敗として数え、先へ進む。
- 失敗が `maxFailures` を超えたら、`maxMinutes` に達したら、実行全体の `maxRequests` を使い切ったら止める。
- 商品ページの読み取りに失敗しても、カタログの実行は失敗にしない。読んだ件数・失敗・止めた理由を生スナップショットの `pageInventory` に残し、警告にする。

### 数の読み方

- M5Stack 公式: スクリプトの数を先に読み、同じバリエーションの `<option data-inventory>` があれば一致を確かめる。食い違えば、そのページは読めなかったものとする。スクリプトが無ければ `<option>` だけを読む。ページの handle が違えば読まない。記録するのは**段階表示(「10+ In Stock」)ではなく、その元になっているページのデータの数**である。負の数(売り越し)は、数の無い読み取り(`null`)にする。
- スイッチサイエンス: canonical の URL が対象の商品と一致し、「在庫数」がちょうど 1 つあるページだけを読む。「100+」は 100 として記録する。上限の数が 100 以外(「50+」など)なら、そのページは読めなかったものとする。

### 記録の規則

`withPageQuantity`(`src/adapters/productPageInventory.ts`)が 1 つの offer の数を決める。

| 状況 | 記録 | 在庫数の系列 |
|---|---|---|
| `pageInventory` の無いスナップショット(この ADR より前) | `not_exposed` | 変わらない(従来どおり) |
| 読めて数がある | その数(`site_reported`) | 変化点 |
| 読めたが使える数が無い(負の数) | `null` | 「表示なし」の点。線が切れる |
| 読んでいないが、カタログで買えない | `null` | 同上。前の数を「在庫切れ」の横に残さない |
| 読んでいない(今回の組の外、取得失敗、打ち切り) | `quantityUnobserved` | 変化点を作らない。最後の数がそのまま続く |

- `quantityUnobserved` は正規化した `Availability` に、真のときだけ付ける。古いスナップショットの正規化ハッシュは変わらない。

### 「100+」と契約

- 店舗の上限表示は `StoreCapabilities.inventoryQuantityCap`(スイッチサイエンスは 100)で宣言し、公開データでは在庫系列の省略可能なフィールド `cappedAt` として配信する。契約は 1.2.0(マイナー版)。
- 点の形 `[t, quantity]` は変えない。0.7.4 は長さ 2 でない点を拒否するが、未知のフィールドは無視し、メジャー版だけを比べる。そのため 0.7.4 はそのまま読め、「100+」を「100」と表示する。
- 0.7.5 は `count >= cappedAt` の数を「100+」と表示する(グラフの点、「最新の在庫表示」)。上限に達した点を描いたときだけ、見出しに「「100+」は100以上」と書く。UI は店舗名を見ない。
- パネルの「表示在庫数」は「在庫数」に、グラフの見出しは「在庫数の推移（店舗のページが示す数。実在庫を保証しません）」に改める。M5Stack 公式の数はページに見える文字ではないため、「店舗が表示した数」とは書かない。

## 理由

- 在庫数の推移は、秋月・KSY で既に描いている。数がページにある店舗だけ描かないのは、オーナーの求める比較にならない。
- 商品ページの数とカタログの `available` は入口が 2 つになる(ADR-0014 が避けた点)。食い違いの裁定は作らず、カタログが状態(在庫あり・なし)、ページが数、と役割を分けた。買えない商品に前の数を残さない規則だけが、両者をつなぐ。
- 読めなかった回を `null` にすると、分割した店舗では 4 回に 3 回線が切れる。読めなかった回は変化点を作らず、読めた事実(数・数の無いページ・買えない状態)だけを点にした。

## 結果

- 公開後の最初の観測日から、M5Stack 公式は全商品、スイッチサイエンスは在庫ありの 1/4 ずつ数が付く。スイッチサイエンスの全体に数が行き渡るのは約 8 日後(毎日の観測になった #82 以降は約 4 日)。
- 相手への負荷は、M5Stack 公式が 1 観測日あたり約 664 件増、スイッチサイエンスが約 1,460 件増。どちらも 1 件ずつ、前の開始から 1.5 秒以上あけて取る。
- 残るリスク:
  - M5Stack 公式の規約の解釈。
  - スイッチサイエンスの数は最長約 8 日前の値。在庫ありのまま数だけ変わっても、次にその組を読むまで反映しない。
  - 0.7.5 の審査が通るまで、0.7.4 は「100+」を「100」と表示する。
  - M5Stack 公式の記録値(例: 379)は、ページに見える段階表示(「10+」)と違う。
  - 取り込みは時刻順が前提。古いスナップショットを順を崩して取り込み直したときの、`quantityUnobserved` の回を含む在庫系列は確かめていない。
  - テーマが変わって数が読めなくなると、失敗が `maxFailures` を超えて止まり、警告になる。数は `quantityUnobserved` のままで、最後の数が続く。
- テスト:
  - `tests/unit/product-page-inventory.test.ts`: 組の選び方、止める条件、記録の規則。
  - `tests/unit/store-product-pages.test.ts`: 実ページの行(`tests/fixtures/m5stack/product-*-stock-lines.html.gz`)とスイッチサイエンスの保存ページ。
  - `tests/integration/switch-science-crawl.test.ts`、`tests/unit/m5stack.test.ts`: 収集から正規化まで。
  - `tests/db/import.test.ts`: 読まなかった回が変化点を作らない。
  - `tests/contract/publisher.test.ts`: `cappedAt` の配信と検証。
  - `tests/userscript/chart.test.ts`、`tests/userscript/comparison-panel.test.ts`: 「100+」の表示と見出し。

## 追記: 最初の観測の失敗と修正(2026-11-04、#78)

2026-11-03T20:00Z の定期 run(41746960279)が、商品ページを読む最初の観測だった。何も公開されなかった。原因は 3 つ。

- **ワークフロー**: KSY が隔離(終了コード 3)になり、`bash -e` の手順でパイプの終了コードが手順ごと止めた。後の店舗も、デプロイも動かなかった。各店舗の pipeline を `set +e` で囲み、終了コードは `PIPESTATUS` で読む。隔離・失敗は従来どおり店舗ごとに扱い、公開は続く(runbook の「1 店舗が失敗しても、他店舗の公開は止まらない」)。
- **スイッチサイエンス**: 1,388 件中 350 件を読んだところで、失敗が `maxFailures` 50 を超えて止まった。失敗 51 件は、すべて題名が「《お取り寄せ商品》」で始まる商品だった。取り寄せ品のページには在庫数の行が無い(読んだ 51 件すべて。それ以外の読めたページにはすべて行があった)。題名で判定し、取り寄せ品はページを読まない(`showsStockCount`)。在庫ありのまま読まないので `quantityUnobserved` になり、数の系列は作らない。数の無いページを「読めないページ」と扱う読み取り側の規則は変えない。
- **M5Stack 公式**: 291 件を読んだあと、429 ではない応答で `Retry-After: 130` を受けた。フェッチャーの待機上限 120 秒を超えたため再試行しなかった。続く 2 件も待機中として即座に失敗し、3 件連続の失敗で読み取りが止まった。待機上限をコレクター設定 `maxWaitMs`(既定 120000、1000〜600000)にし、M5Stack 公式は 300000(5 分)まで待つ。5 分を超える指示は従来どおり止まる。待った時間も `maxMinutes` 35 に含まれる。

その回の観測(秋月・スイッチサイエンス・M5Stack 公式)は、run の成果物から `reimport_snapshot_from_run` で 1 店舗ずつ取り込み直す。載る数は、M5Stack 公式が 682 件中 291 件、スイッチサイエンスが 1,388 件中 350 件(取り寄せ品の失敗が `maxFailures` 50 を超えて止まった)。残りは `quantityUnobserved` で、以後の観測で埋まる。

- テスト: `tests/unit/m5stack.test.ts`(出荷設定で 130 秒を待って全件読む、既定の 120 秒では止まる、`maxWaitMs` の範囲)、`tests/integration/switch-science-crawl.test.ts`(取り寄せ品のページを要求しない)。

## 追記(2026-11-08, ADR-0030)

観測が毎日になったので、組の回転は観測日の番号をそのまま使う(`shards` は 4 のまま)。1 商品の数の更新は、スイッチサイエンスが約 4 日に 1 回、M5Stack 公式が毎日になる。1 回の読み取り件数と時間は変わらない。切り替えの日だけ、読む組が隔日の番号のときと連続しない。

## 更新(2026-11-10, Issue #93 案 C)

Shopify 共通コレクターは、買えるバリエーションが 1 つも無い商品の商品ページを読まない。カタログの `available` がすべて偽の商品は、ページを読んでも正の数が付かないためである。1 つでも買えるバリエーションがある商品は、これまでどおりすべてのバリエーションを対象にして読む(ここまでの本文の「M5Stack 公式は全商品」は、この更新で「買える商品」に変わる)。

- 読まなかった商品の記録は、上の表の「読んでいないが、カタログで買えない」の行のとおり。`quantity` は `null`、`quantitySemantics` は `site_reported`、`quantityUnobserved` は付けない。アダプターは変えていない。
- 根拠の実測: 2026-11-09 の M5Stack 公式は 683 商品中 219 商品が買えず、ページの取得は 1 日あたり約 7 分が無駄だった。
- 1 観測日あたりの負荷は、対象が 664 件から買える商品の数(2026-09-12 の保存カタログでは 443 件、約 33% 減)になる。上の「約 664 件増」は当時の見込みとして残す。確定値は、更新後の最初の run の `productPagesSelected` で確かめる。
- 1 回限りの影響: 更新後の最初の run で、これらの商品の記録済みの `0` が「表示なし」の点(線が切れる)に変わる。以後の run は毎回「表示なし」のまま変化点を作らない。
- `productPagesSelected` と `eligible` は読む対象の件数で数える。警告の文面(`Product pages stopped early (n/m read)`)の m も同じ。
- テスト: `tests/unit/m5stack.test.ts`(買えない商品のページを要求しない、一部だけ買える商品は全バリエーションを読む、`productPagesSelected` が買える商品の数、アダプターを通した `quantityUnobserved` の有無)。

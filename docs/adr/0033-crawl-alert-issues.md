# ADR-0033: 観測できなかった店舗は Issue で知らせ、書き込み権限は別ジョブに置く

状態: 採用 / 2026-11-10 / Issue #92

関連: ADR-0004(不完全なクロールは取り込まない)、ADR-0006(状態の公開)、ADR-0030(毎日観測)、`scripts/crawl-alerts.ts`、`scripts/run-budget.ts`、`.github/workflows/crawl-publish.yml`、[runbook](../runbook.md#観測できなかった店舗の通知と-run-の長さ)

## 背景

- 店舗が**失敗**(終了コード 1)するとジョブが赤くなり、GitHub の通知が出る。**隔離**(終了コード 3)は公開を止めないのでジョブは緑のまま終わり、warning 注釈と summary の 1 行しか残らない。2026-11-09 にせんごくが隔離されたとき、痕跡はその注釈だけだった。
- ADR-0030 以降は全店舗を毎日観測するので、観測できなかった 1 日は拡張機能のグラフの穴になる。気づくのが遅れた日数だけ穴が広がる。
- 全店舗を 1 つの直列ジョブ(上限 240 分)で回している。通常の 1 日は 175〜184 分(上限の 73〜77 %)で、上限に近づいても最初の兆候は「ジョブがキャンセルされた」になる。

## 決定

1. **観測できなかった店舗は、店舗ごとに 1 件の Issue で知らせる。** 対象は `quarantined` と `failed`。題名 `Crawl alert: <store> was not observed`、ラベル `crawl-alert`、担当者はリポジトリの所有者。開いている Issue がある店舗が再び観測できなければ、その Issue にコメントを足す。
2. **次に観測できた run が Issue を閉じる。** 観測できたとは、`collect` が成功し結果が `published` か `unchanged` であること。`--republish` だけの run は観測していないので、作りも閉じもしない。
3. **隔離ではジョブを失敗させない。** 隔離された店舗以外の公開は続く、という従来の動作を変えない。
4. **書き込み権限は別ジョブ `alerts` に置く。** `crawl` ジョブは npm の依存を動かし、外部のページを解析する。そこに `issues: write` のトークンを置かない。`alerts` は `contents: read` と `issues: write` だけを持ち、`npm ci` をせず、依存のない 1 本のスクリプトを素の `node` で動かす。
5. **店舗由来の文字列はデータとして扱う。** レポートの理由文はコードブロックに入れ、バッククォートと `<!--` を無効化し、長さと行数を切る。`gh` はシェルを通さず引数配列で呼び、本文は標準入力で渡す。
6. **状態は Issue 自身に持たせる。** 本文 1 行目のマーカー `<!-- crawl-alert store=<store> -->` で店舗を、`<!-- crawl-alert run=<run id> -->` で通知済みの run を識別する。操作は「あるべき状態との差分」なので、ジョブを回し直しても同じ run の通知は重複しない。途中で失敗しても次の run が続きを行う。
7. **0 と 3 以外の終了コードはすべて失敗として扱う。** メモリ不足やシグナルでの異常終了(134、137 など)は何も観測していない。従来は 1 だけを失敗としていたので、これらは成功として通っていた。
8. **run の長さは warning だけにする。** ジョブ開始からの経過を上限と比べ、summary に出し、80 %(192 分)を超えたら warning 注釈を出す。Issue は作らない。

## 採らなかった案

- **隔離でジョブを赤くする。** 通知は届くが、「赤 = 公開されなかった店舗がある」という意味が薄れ、隔離のたびに `deploy` の `always()` に頼ることになる。隔離は設計上の正常系(ADR-0004)なので、状態ではなく通知で扱う。
- **店舗 × 日ごとに Issue を作る。** 障害が数日続くと Issue が日数分増える。1 件にコメントを重ねるほうが、いつから観測できていないかを 1 か所で読める。
- **`crawl` ジョブに `issues: write` を足す。** 手順は 1 つ減るが、書き込みトークンが依存パッケージと外部入力を扱うジョブに入る。
- **Issue を検索 API で探す。** 検索インデックスは反映が遅れるので、直後の回し直しで重複を作りうる。ラベルで開いている Issue を一覧する。
- **run の長さでも Issue を作る。** 80 % 前後を行き来すると毎日開閉する。現在は cover クロール(ADR-0032)で余裕が増える見込みなので、まず warning で様子を見る。

## 影響

- 通知が届く経路は GitHub の Issue 通知(割り当て)になる。ラベル `crawl-alert` は最初の Issue を作るときにジョブが作る。
- ワークフローに `actions/download-artifact`(v8.0.2、SHA 固定)が 1 つ増える。npm の依存は増えない。
- `JOB_LIMIT_MINUTES` と `timeout-minutes` は同じ値を 2 か所に書く(`timeout-minutes` に式を書けないため)。テストが一致を検査する。
- 実ジョブでの確認(Issue の作成・通知・自動クローズ、`### Run length` の表示)は、導入後の最初の定期 run と、次に隔離または失敗が出た run で行い、journal に記録する。
